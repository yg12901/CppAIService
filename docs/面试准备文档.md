## 开场 30 秒电梯稿（整个项目，第一部分能撑起来的那一层）

> 这是一个用 C++ 写的 AI Agent 服务。底层用 Muduo 做 TCP 网络，我们自己在上面解析 HTTP、做路由和登录鉴权。服务是主从 Reactor：1 个主线程只负责接连接，4 个 IO 线程各自盯自己分到的连接。浏览器发来的请求可能一次到不齐，我们在每条连接上挂一个 HTTP 状态机，半包就先记下进度，齐了再进业务。登录用 Cookie Session；聊天窗口是另一套 sessionId，每个窗口在内存里留一份对话历史，这样多轮对话才能接得上。长请求（调大模型）如果堵在 IO 线程里会拖死这条线程上的所有连接，所以流式对话会丢到单独的 worker 池里跑。

如果面试官说「先随便讲讲这个项目」，就用上面这段，然后等他追问。不要一上来就讲策略模式、MCP、读写锁——那些是后面模块。

### 1. 给完全没有技术背景的人讲明白

把它想成一家餐馆。

**Muduo** 是大门和传菜员：客人进门（TCP 连接建立），说话（发来一串字节）。Muduo 不管这句话是不是人话，它只保证「有人说话了就通知后厨」。

**HTTP 解析** 是翻译：把乱码似的字节翻译成「这桌要点什么菜」。麻烦在于：客人可能一次只说出半句话（半包）。翻译员必须记住「他说到哪了」，等下半句到了再拼，不能把半句话当成点菜单去炒。

**路由** 是菜单：`/login` 去收银台，`/chat/send` 去炒菜窗口。看方法和路径，送到对应窗口。

**鉴权** 是门口手环：登录成功发一个 Cookie 手环，上面写着「已登录、你是几号客人」。以后每次来先看手环，没有就请回去登录。

**多 IO 线程** 是 1 个迎宾 + 4 个传菜员。迎宾只负责领位：新客人来了，按 1、2、3、4、1、2……轮流分给传菜员。**客人一旦坐下就不换桌。** 所以同一桌的对话永远是同一个传菜员在听，不会两个人同时听同一桌而听乱。

**多轮会话** 是桌上那本点菜单：上一句问了什么、店员回了什么都记着。下一句才能接上「那再辣一点」而不是当成新客人。

**流式 worker 池** 是后厨：有的菜要等很久（调大模型几秒钟）。如果传菜员自己在桌边干等，他名下别的桌就没人管了。所以「等得久的菜」交给后厨 8 个人炒，传菜员把菜单一递就去伺候别的桌；菜好了再一碟一碟端上来（打字机效果）。

### 3. 程序怎么开张（启动顺序）

对应代码：

- `AIApps/ChatServer/src/main.cpp` → `main()`
- `AIApps/ChatServer/src/ChatServer.cpp` → 构造函数、`initialize()`、`start()`
- `HttpServer/src/http/HttpServer.cpp` → 构造函数、`start()`、`initialize()`

**面试回答：**

进程起来之后做这几件事，顺序不能乱：

1. 构造 `ChatServer`。构造时就会初始化：MySQL 连接池、登录 Session 存储、CORS 中间件、把 12 个 URL 挂到路由表、拉起 8 线程的流式 worker 池、在主 loop 上挂一个 5 秒一次的 SSE 心跳。
2. `setThreadNum(4)`。这行**只是记下数字**，IO 线程还没真正创建。
3. 睡 2 秒。代码里没写原因，我理解是给 MySQL / RabbitMQ 一点启动时间。生产上应该做健康检查重试，不该硬 sleep。
4. `initChatMessage()`：从数据库把历史聊天灌回内存，这样重启后多轮对话还能接上。
5. 先启动 RabbitMQ 消费线程（2 个），再 `server.start()`。因为 `start()` 里主线程会进入 `mainLoop_.loop()` **再也回不来**，消费池必须先起来。
6. `TcpServer::start()` 这时才真正 listen，并按刚才记下的 4 创建 4 个 IO 线程。主线程卡在事件循环里迎接新连接。

**可能追问：为什么 MQ 消费要在 `server.start()` 之前？**

因为 `HttpServer::start()` 最后一句是 `mainLoop_.loop()`，这是死循环。写在它后面的代码主线程执行不到。

**可能追问：构造函数里有个签名坑？**

有。`ChatServer` 把 Muduo 的 `Option` 传到了 `HttpServer` 的第三个参数，而第三个参数其实是 `bool useSSL`。默认 `kNoReusePort` 是 0，碰巧 SSL 关着。如果有人改成 `kReusePort`（值为 1），会误把 SSL 打开。这是参数顺序没对上，默认路径碰巧安全。

对应：

```cpp
// ChatServer.cpp 构造
httpServer_(port, name, option)

// HttpServer.h 真正签名
HttpServer(int port, const std::string& name, bool useSSL = false, Option option = kNoReusePort);
```

### 4. Muduo 负责到哪一层，HTTP 是谁做的

**面试回答：**

Muduo 是网络库，只管 TCP：接连接、收字节、发字节、用 epoll 等事件。它不知道什么是 GET、什么是 `/chat/send`。

我们在 Muduo 的「有数据了」回调里，自己写了一个 HTTP 状态机 `HttpContext`：先拆请求行，再拆头，再按 `Content-Length` 等 body。拆完才进路由和业务。

可以把它说成三层：

```
浏览器
  → TCP 字节流          （Muduo TcpServer）
  → HTTP 请求对象        （我们的 HttpContext / HttpRequest）
  → 某个业务 Handler     （Router 分发）
```

**为什么不用 nginx / Boost.Beast？**

项目目标是把 Reactor 和高并发 IO 吃透。Muduo 是「一个线程一个事件循环」这套模型，和简历上的多线程高并发能对上。Beast 能少写解析，但面试时讲不出连接怎么分线程、半包怎么拼。我们前面没有把服务挂到 nginx 后面，本地直接听 80。

**对应代码：**

- 注册回调：`HttpServer.cpp` 的 `initialize()`，`setConnectionCallback` / `setMessageCallback`
- 有数据：`onMessage()`
- 拆包：`HttpContext.cpp` 的 `parseRequest()`
- 进业务：`onRequest()` → `handleRequest()`

### 5. 多 IO 线程到底怎么工作（高频追问）

#### 5.1 先纠正一个错觉

**不是**「4 个工人抢一个任务队列，谁闲谁领下一个 HTTP 请求」。

**是**「4 个传菜员，每人盯自己分到的那几桌客人。一桌客人从进门到结账，永远是同一个传菜员」。

Muduo 自己的注释写了：`setThreadNum(N)` 之后，新连接 **round-robin（轮流发牌）** 分给 N 个 IO 线程。

#### 5.2 线程账（被问「你到底几个线程」就报这个表）

| 角色 | 数量 | 干什么 | 是不是 IO 线程 |
|---|---|---|---|
| 主 EventLoop | 1 | 只 listen/accept；另外跑 SSE 心跳定时器 | 迎宾，几乎不跑业务 |
| IO 线程 | 4 | 读连接、拆 HTTP、跑 Handler、真正 write 套接字 | 是 |
| StreamWorkerPool | 8 | 流式场景下等大模型（curl） | **不是**，普通线程，没有 epoll |
| RabbitMQ 消费 | 2 | 异步写库 | 不是 |
| DB 探活 | 1 | 定期 ping 连接 | 不是 |

#### 5.3 连接怎么分、回调在哪跑

启动：`main.cpp` 里 `setThreadNum(4)` → `HttpServer::start()` 里 `server_.start()` 才真正起 4 个线程，每个线程自己一个 `EventLoop`（里面是 epoll 死循环）。

新连接来了：

```
浏览器 TCP 三次握手
  → 主线程 accept 得到 sockfd
  → getNextLoop()：第 1 个连接给线程 0，第 2 个给线程 1……第 5 个又回线程 0
  → 把这个 fd 交给那个 IO 线程的 epoll
  → 从此这条连接只归它
```

这条连接上以后每一次：

- 有数据 → 这个 IO 线程被唤醒
- 调 `HttpServer::onMessage` → 还在这个线程
- 解析 HTTP、走路由、跑 `ChatSendHandler::handle` → 还在这个线程

**同一条连接上的事不用加锁**，因为同时只有这一个线程会碰它。

**全局的东西必须加锁**，比如所有用户的会话表 `chatInformation`、登录 Session 的 map。4 个 IO 线程会同时改它们。不要说成「Muduo 一个连接一个线程所以全局 map 也不用锁」——那是错的。

#### 5.4 每个 IO 线程在干什么（人话）

```
for (;;) {
    睡在 epoll 上，等「我名下某条连接可读或可写」；
    哪个 socket 有事，就跑我们注册的回调；
    回调跑完，再回去睡。
}
```

所以：**IO 线程同时只能执行一个回调。** 它名下可以挂成千上万条空闲连接（epoll 擅长看很多 fd），但一旦某个 Handler 里卡住几秒，这几秒里它名下别的连接都没人读。

#### 5.5 为什么还要 8 个 worker（和 IO 线程的关系）

默认聊天是流式。`ChatSendHandler` 在 IO 线程里只做三件事就 **return**：

1. 写 SSE 响应头
2. 把「去调大模型」这个任务 `submit` 给 `StreamWorkerPool`
3. 告诉框架：这是流式，你不要再统一发包（避免和我们自己 send 重复）

真正的 `chat()` / curl 等模型，跑在 worker 线程。worker 每收到一个字，调 `conn->send`。Muduo 发现「当前线程不是这条连接的 IO 线程」，会把这次发送**投递回连接所属的那个 IO 线程**再真正 write。所以套接字不会被两个线程同时写乱。

非流式路径（`stream=false`，或 RAG 不支持流）会在 IO 线程里直接 `chat()` 干等。这是短板，面试主动说。

#### 5.6 面试回答（整段可背）

> 我们是主从 Reactor。主线程只接连接，4 个 IO 线程各自一个事件循环。新连接轮询分下去，一条连接一生只在一个 IO 线程上，所以这条连接的收发和 HTTP 解析不用加锁。高并发指的是同时能挂很多连接，不是同时能跑很多个阻塞业务。调大模型这种要等几秒的事，如果放在 IO 线程里，这个线程名下所有连接都会卡住，所以流式请求会丢到 8 线程的 worker 池；worker 里 send 会由 Muduo 转回连接所属 IO 线程。全局的会话表仍然要加锁，因为多个 IO 线程会同时访问。

#### 5.7 可能追问速查

**Q：4 个线程是不是同时只能处理 4 个请求？**  
不是。4 个线程可以同时看着很多空闲连接。限制是：同时卡在 Handler 里的最多 4 个（每个 IO 线程同一时刻只能跑一个回调）。流式把等待挪到 worker 上，IO 线程很快就能回去盯别的连接。

**Q：同一个用户连着发 3 个请求，会不会到 3 个 IO 线程？**  
如果还是同一条 TCP（HTTP keep-alive），三次都在同一个 IO 线程里排队。如果浏览器另开了连接，才可能分到别的线程。

**Q：主线程还处理业务吗？**  
`setThreadNum(4)` 之后，主 loop 几乎只 accept。Muduo 规定：数字是 0 才表示所有 IO 都在主线程。

**Q：worker 算不算第 5～12 个 IO 线程？**  
不算。它们没有 epoll，不负责读浏览器数据。只是普通线程，专门「等 curl」。

**Q：为什么是 4 不是 8？**  
经验上 IO 密集大致按核数来。没有正式压测报告，不能说这是最优。真正怕的是 Handler 阻塞 IO 线程，这个我们用流式剥离来解。

**对应代码：**

- `main.cpp`：`setThreadNum(4)`
- `HttpServer.h`：`server_.setThreadNum`
- Muduo `TcpServer.h`：注释写明 round-robin
- `ChatSendHandler.cpp`：流式 `submit` + `setStreaming(true)`；非流式直接 `chat()`
- `SseChannel.h`：`conn->send` 由 Muduo 转到所属 IO 线程

### 6. 半包：一条连接、两次 onMessage（高频追问）

#### 6.1 先把话说对（容易说错）

**错：** 第一次只来一半就返回失败，把前一半存着，等拼齐了再一起发给别人。

**对：** 第一次一半到了，解析算**成功**，只是**还没齐**。前一半躺在这条连接自己的缓冲区里，进度记在这条连接自己的解析器里。第二次字节补到同一块缓冲区后面。拼齐后在**本机**进 Handler，不是把请求再发一遍。对外发的是响应。

对照：

| 容易说错的词 | 应该说 |
|---|---|
| 返回失败 | 语法 OK，但没收齐。不 400、不断连接、不进 Handler |
| 存一份再发出去 | 字节本来就在连接的 `buf` 里，新字节是接在后面，不是客户端重发 |
| 拼起来再一起发 | 拼起来后就地处理请求；发送的是 HTTP 响应 |

#### 6.2 为什么会半包（人话）

TCP 是一根水管，只保证字节按顺序流，**不保证一次刚好送来一份完整 HTTP**。浏览器以为自己发了一整张点菜单，网卡可能先送到「请求行 + 头 + 半截 JSON」，过一会儿才送到剩下几个字。

所以必须按连接记住：「我拆到哪了、body 还差几字节」。

#### 6.3 这条连接上有三样东西

连接一建立（`onConnection`，连接成功时）：

```cpp
conn->setContext(HttpContext());
```

之后每次有数据（`onMessage`）：

1. 从连接上取出**同一个** `HttpContext`
2. 用连接的输入 `buf` 继续 `parseRequest`
3. 只有 `gotAll()` 为真才 `onRequest` 进业务，然后 `reset()` 准备这一条连接上的下一单

```
这条 TCP 连接（永远粘在某一个 IO 线程上）
├── buf                 已经到达的字节堆在这
├── context.state_      解析到哪一步（请求行 / 头 / 体 / 完成）
└── context.request_    已经抠出的 method、path、headers、body
```

状态四个格子：

```
kExpectRequestLine → kExpectHeaders → kExpectBody → kGotAll
等第一行 \r\n         等一个个 header    等齐 Content-Length     可以进业务
```

因为连接粘线程，两次 `onMessage` 不会并行改同一个 `HttpContext`，这里不用加锁。

#### 6.4 用 POST /chat/send 走一遍（Body 被拆成两次）

假设 body 是 20 字节的 `{"question":"你好"}`。

**第一次 onMessage，只到了 14 字节 body：**

- 状态机拆完请求行、拆完头，看到 `Content-Length: 20`，进入「等 body」
- 缓冲区里只有 14 字节，小于 20
- `parseRequest` 返回 true（没写坏）
- `gotAll()` 为 false → **Handler 一次都不调**
- IO 线程回去 epoll 睡觉
- 留下：`state_ = kExpectBody`，path 已经是 `/chat/send`，半截 JSON 还在 `buf` 里

**第二次 onMessage，补上剩下 6 字节：**

- 还是同一个 IO 线程、同一个 `HttpContext`、同一块 `buf`（新字节 append 在后面）
- 一进来就是「等 body」，现在 20 >= 20
- 把 20 字节放进 `request_.body`，状态变成 `kGotAll`
- 这才 `onRequest` → 路由 → `ChatSendHandler`
- 最后 `reset()`，状态打回「等请求行」，准备这条连接上的下一个 HTTP 请求

**请求行被拆开也是同一套逻辑：** 第一次只有 `POST /chat/se`，找不到 `\r\n`，什么都不消耗，状态仍是「等请求行」，字节全部留在 `buf`。第二次补齐成完整一行，才往下走。原则：**找不到这一段的结束符，就动也不动。**

#### 6.5 面试回答（整段可背）

> TCP 不保证一次读就是一个完整 HTTP 请求。我们在每条连接上挂一个 HttpContext 状态机，字节堆在这条连接的 Buffer 里。第一次不够，只更新「我解析到哪了」，不进业务，也不报错。第二次还在同一个 IO 线程里，从上次的状态接着拆，齐了才进 Handler，然后把状态机复位。半包不是失败，也不是把半截请求再转发一次。

#### 6.6 半包相关追问

**Q：进度存在线程上还是连接上？**  
必须在连接上。一个 IO 线程管很多连接，存在线程上会串台。

**Q：第一次返回值是失败吗？**  
不是。失败是 HTTP 语法错，会 400 并关掉连接。半包是「语法对、数据不够」。

**Q：谁负责把两次数据拼起来？**  
Muduo 的 `Buffer` 自动把新字节接在旧字节后面。我们只判断「现在够不够 Content-Length」。

**Q：GET 会半包吗？**  
会，如果请求行或头被拆开。GET 通常没有 body，头收齐（空行到来）就算 `kGotAll`。

**Q：只认 Content-Length 有什么问题？**  
不支持 `Transfer-Encoding: chunked`。课程项目够用，不要说完整实现了 HTTP/1.1。

**Q：一次读到两个完整请求（粘包）怎么办？**  
我们 `gotAll` 之后 `reset` 了，但 **没有** 在同一次 `onMessage` 里循环把缓冲区剩的再解析一遍。第二份请求要等这条连接上下一次可读。这是缺口。补法是 `while (还能 parse 且 gotAll) { 处理；reset; }`。半包处理是对的，粘包循环没收口。

**对应代码：**

- `HttpServer.cpp`：`onConnection` 挂 context；`onMessage` 里 parse / gotAll / reset
- `HttpContext.h`：四个状态
- `HttpContext.cpp`：`parseRequest`；body 不够就 `return true`；请求行找不到 CRLF 就停

### 7. 路由分发

**面试回答：**

启动时把「方法 + 路径」登记进一张哈希表，例如 POST + `/chat/send` 对应 `ChatSendHandler`。来了一个请求，用同样的键去查，平均 O(1) 找到 Handler 就调 `handle`。找不到返回 404。

框架还写了正则动态路由，能把 `/user/:id` 这种拆出路径参数。我们业务这十来个接口全是写死的路径，**没有走正则那条分支**。面试不要吹「我们用了 RESTful 动态路由」。

路径很少，哈希就够。上万动态路径再考虑前缀树，现在没必要。

**对应代码：**

- 注册：`ChatServer.cpp` 的 `initializeRouter()`
- 查找：`Router.cpp` 的 `route()`，先 `handlers_` 哈希，再扫 `regexHandlers_`
- 键：`Router.h` 的 `RouteKey`（method + path）

常见接口（记个印象，不必背全）：

| 方法 | 路径 | 干什么 |
|---|---|---|
| POST | `/login` `/register` `/user/logout` | 登录注册登出 |
| POST | `/chat/send` | 往已有窗口发消息 |
| POST | `/chat/send-new-session` | 新建窗口并发送 |
| POST | `/chat/history` | 拉某个窗口历史 |
| GET | `/chat/sessions` | 窗口列表 |
| POST | `/upload/send` | 图像识别 |
| POST | `/kb/upload` | 文档灌进共享知识库 |
| POST | `/kb/job-status` | 查询索引任务 |
| POST | `/chat/tts` | 语音合成 |

**可能追问：路由要不要加锁？**  
启动时注册完就不再改，运行期只读，不用锁。

### 8. 请求鉴权

**面试回答：**

不是 JWT。是服务端 Session + Cookie。

登录成功后：

1. 从 Cookie 里取 sessionId，没有就新建一个 32 位十六进制随机 ID
2. 通过 `Set-Cookie: sessionId=...; Path=/; HttpOnly` 发给浏览器
3. 在内存 Session 里写入 `userId`、`username`、`isLoggedIn=true`，还有 `canChat/canImage/canTts`
4. 默认 1 小时过期，每次请求 `refresh()` 续期

之后每个业务 Handler 开头：取出 Session，看 `isLoggedIn` 是不是 `true`，不是就 401；再看对应功能权限，不是就 403。

**和简历的出入，主动说：**  
鉴权没有做成中间件。中间件链现在只挂了 CORS（浏览器跨域预检 OPTIONS 会在中间件里直接返回）。鉴权是每个 Handler 手写 if，漏写就是裸奔。更合理的是做 `AuthMiddleware`，白名单放行登录注册。

**对应代码：**

- 取/建 Session：`SessionManager.cpp` 的 `getSession()`
- 内存存储：`MemorySessionStorage`（进程内 map，**没加锁**）
- 登录写入：`ChatLoginHandler.cpp`
- 业务检查：`ChatSendHandler.cpp` 开头
- 过期：`Session.h` 默认 `maxAge = 3600`

#### 鉴权追问

**Q：为什么不用 JWT？**  
单机内存 Session 实现简单，登出可以立刻 `destroySession` 作废。JWT 要自己管过期和密钥。这个体量没必要。多机部署时 Session 得放到 Redis，那是下一步。

**Q：Cookie 安全吗？**  
HttpOnly 有，防一点点 XSS 偷 Cookie。没有 Secure、没有 SameSite，服务默认是明文 HTTP 80。代码里有 SSL 封装但没打开。上公网必须 HTTPS + Secure Cookie。

**Q：密码怎么存的？**  
查询是用户名密码一起比对，库里像是明文。演示项目欠账，生产必须加盐哈希。

**Q：Session 存在内存、多 IO 线程同时登录会怎样？**  
`MemorySessionStorage` 的 map 没有锁，理论上有数据竞争。不要用「连接粘线程」来洗白——不同连接可以同时碰这张全局表。生产应加锁或改 Redis。

### 9. 多轮会话（两套 ID，别混）

这是第一部分里最容易讲混的点。

| 名字 | 回答哪个问题 | 存在哪 |
|---|---|---|
| Cookie 里的 sessionId | 你是不是已经登录的那个用户 | 浏览器 Cookie + 进程内 Session 存储 |
| 聊天的 sessionId | 这是哪一个对话窗口 | 请求 JSON 体；内存二级 map + 数据库 `chat_message` |

一个用户可以同时开多个聊天窗口，所以内存是：

```
userId → 聊天 sessionId → AIHelper（里面有 messages 历史）
```

`messages` 是这个窗口的聊天记录数组。每条是 `ChatMessage`：`role`（`"user"` / `"assistant"` / `"system"`）+ 内容 + 时间戳。组模型请求时把整段历史带上，role 直接读字段，不靠下标猜。

（早期实现是 `pair(内容, 时间)`，用偶数下标当用户、奇数当下 AI。已经改掉，见第二部分第 8 节。）

发消息：`/chat/send` 带上聊天 sessionId，找到这份 `AIHelper` 继续 append。  
新建窗口：`/chat/send-new-session` 生成一个新的聊天 sessionId，再发第一句。  
重启：`readDataFromMySQL()` 按时间升序把表灌回内存，重启后还能接上（库里成功写入的那些）。

**为什么聊天历史还要在内存里留一份？**  
每轮都要把全量历史发给模型。内存数组拼 JSON 比每次 SELECT 再拼更快。代价：内存只涨不跌，和库可能短暂不一致（落库是异步的，后面模块再细讲）。

**短板，主动说：**  
没有上下文截断，聊得越久越贵、内存越大。生产应做滑窗或摘要。role 已经写在每条消息上，重启恢复时会把库里的 `is_user` 转成 role，不会再丢。

**对应代码：**

- 结构：`ChatServer.h` 的 `chatInformation`
- 发送：`ChatSendHandler.cpp` 的 `getOrCreateChatHelper`
- 恢复：`ChatServer.cpp` 的 `readDataFromMySQL`
- 历史数组：`AIHelper.h` 的 `messages`

### 10. 一次请求完整走路（面试画图用）

以「已登录用户往某个窗口发一句」为例。

```
浏览器 POST /chat/send
Cookie: sessionId=登录那个
Body: { question, sessionId: 聊天那个, modelType }

主线程：只 accept（这条连接可能早就建好了，走 keep-alive 就没有这一步）

拥有这条连接的 IO 线程：
  内核可读 → onMessage
  HttpContext 拆包
    半包？记下进度，return，回去睡觉
    齐了？继续
  CORS 中间件（普通 POST 几乎没事）
  Router 哈希命中 ChatSendHandler
  看登录 Session → 401 / 看 canChat → 403
  用 userId + 聊天 sessionId 拿到 AIHelper（带历史）
  流式：写 SSE 头，任务丢 worker，IO 线程立刻回去
  非流式：就在这个 IO 线程里等模型，再一次性 JSON 返回

worker（仅流式）：
  curl 调模型，每来一个字 conn->send
  Muduo 把 send 转回该连接的 IO 线程真正写出
```

### 12. 第一部分面试题库（按「只看简历的人会不会问」收的）

下面每题都按面试说法写。先用「短答」应付；他追问再看「展开」。

---

#### Q1. 介绍一下这个项目的网络层？

**短答：**  
底层 Muduo 管 TCP 连接和收发。我们自己解析 HTTP、做路由和 Session 鉴权。1 个主线程接连接，4 个 IO 线程处理各自的连接。

**展开：** 见第 4、5 节。

**别说：** 「我们用 Muduo 当 HTTP 服务器，它自带路由。」Muduo 不带 HTTP。

---

#### Q2. 为什么用 Muduo，不用现成 HTTP 库？

**短答：**  
想把 Reactor、连接怎么分线程、半包怎么拼这些事吃透。Muduo 的 one loop per thread 和简历上的高并发模型一致。现成库能少写代码，但讲不出这些细节。

**追问为什么不用多进程 nginx 反代？**  
可以反代，当前是课程项目直接听 80。生产上前面加 nginx 做 TLS 和静态资源更常见。我们代码里有 SSL 封装但没启用。

---

#### Q3. 路由怎么做的？会不会成为瓶颈？

**短答：**  
方法加路径做键，哈希表查找，接口就十来个，不会成为瓶颈。动态路由框架写了但业务没用。

**追问为什么不用前缀树？**  
路径少且静态，哈希更简单。路径量上来、大量 `/:id` 再换。

---

#### Q4. 鉴权怎么做的？

**短答：**  
服务端 Session，Cookie 里带随机 sessionId。登录后内存里记 isLoggedIn。每次请求先查这个标记。不是 JWT。

**追问登出怎么立刻失效？**  
删掉服务端这份 Session，Cookie 就算还在也对不上。JWT 默认做不到这么干脆。

**追问为什么不做成中间件？**  
图快抄到每个 Handler 了。风险是漏写。中间件链是现成的，CORS 已经挂上，鉴权本可以同样挂。这是我知道的短板。

---

#### Q5. 多线程模型具体是怎样的？

**短答：** 用第 5.6 节那段。

**追问 4 个线程是业务线程池吗？**  
不是。是 4 个 IO 事件循环。连接粘在其中一个上，不是抢任务。

**追问会不会死锁？**  
单条连接的收发没有锁。全局表有锁。锁的设计是后面模块（读写锁），第一部分先说「全局共享状态必须加锁」。

---

#### Q6. 怎么支持高并发？有没有压测数据？

**短答：**  
设计上：epoll 盯很多连接、连接粘线程减少锁、路由 O(1)、登录态内存读、长请求不占 IO 线程。没有正式压测，不能报 QPS。这是单机课程项目。

**别报假数字。** 诚信比「我测过十万 QPS」更加分。

---

#### Q7. HTTP 请求一次没收全怎么办？

**短答：** 用第 6.5 节那段。强调：不是失败，不是重发。

**追问状态存在哪？** 连接上的 HttpContext + Buffer。  
**追问为什么不存在线程上？** 一个线程多条连接，会串。  
**追问粘包呢？** 承认没循环解析，是缺口。

---

#### Q8. 多轮对话上下文存在哪？重启丢不丢？

**短答：**  
热路径在内存，每个聊天窗口一份消息数组。落库是异步的。启动时从库按时间灌回来，所以重启不丢已经入库的。

**追问为什么不每次查库？**  
每轮都要带全量历史给模型，内存拼更快。代价是内存增长、和库短暂不一致。

---

#### Q9. 登录 Session 和聊天 sessionId 为什么两套？

**短答：**  
一个答「你是谁」，一个答「哪一次聊天」。一个用户多个窗口，所以是用户下面再挂多个聊天 ID。Cookie 跟登录绑定，不能拿来当聊天窗口 ID，否则多窗口隔离麻烦，Cookie 也会被撑爆。

---

#### Q10. IO 线程里跑业务最大的风险是什么？

**短答：**  
事件循环不能阻塞。非流式聊天会在 IO 线程里等模型几秒，这几秒这个循环上的连接都没人处理，半包的下一截也读不了。流式已经改成 IO 线程只写头、把等待丢到 worker。图像识别仍是 IO 线程里同步推理（后面模块会讲，简历那句图像异步没做）。

**追问为什么不全部丢线程池？**  
登录、拉历史这种短请求，多一次排队未必更快。只有长尾值得剥离。

---

#### Q11. 能开多个进程做水平扩展吗？

**短答：**  
现在不行。登录 Session、聊天内存上下文、在线用户表都在单机内存。多开实例会各记各的：掉登录、上下文断裂、能重复登录。要扩展得把这些搬到 Redis 或按用户分片。

---

#### Q12. Keep-alive 下同一条连接多个请求怎么处理？

**短答：**  
解析完一个请求会 `reset` 状态机，这条连接继续留着，下一个请求还从「等请求行」开始。连接仍然粘在原来那个 IO 线程。如果两个请求一次到齐（粘包），第二份可能要再等一次可读，这是实现上的缺口。

---

#### Q13. Handler 里可以直接在别的线程写 socket 吗？

**短答：**  
可以调 `conn->send`，Muduo 会判断：不是这条连接的 IO 线程，就把发送任务投递回去。worker 里推 SSE 就是这么做的。不要自己在 worker 里直接 `write(fd)`。

---

#### Q14. 主线程的心跳是干什么的？（简历没写，可当加分）

**短答：**  
流式等模型时可能十几秒没有字节，中间的 nginx/负载均衡会以为连接死了。主 loop 每 5 秒扫活跃流，空闲超过 10 秒补发 SSE 注释行 `: ping`，客户端会忽略，但连接保活。这是简历没写的点，被问到流式再提。

---

#### Q15. CORS 中间件是干什么的？和鉴权什么关系？

**短答：**  
浏览器跨域时会先发 OPTIONS 预检。CORS 中间件拦下来直接回允许跨域的头，不进业务。它**代替不了鉴权**。没登录照样不该能调 `/chat/send`。

---

#### Q16. 如果面试官问「你这个 HTTP 解析跟 nginx 比差在哪」？

**短答：**  
我们只覆盖了课程需要的子集：按行拆请求、用 Content-Length 读 body、keep-alive 靠 Connection 头。没有 chunked、没有 pipeline 循环、没有完善的超时掐半包连接。半包状态机这条思路和正规实现是一样的，完整度差一截。

### 14. 第一部分一句话背诵卡

- Muduo 管连接，我们管 HTTP。
- 1 个迎宾 + 4 个传菜员；客人坐下不换桌。
- 半包：进度挂在连接上，不够就睡，齐了再进业务；不是失败，不是重发。
- 路由就是菜单，哈希查找；动态路由写了没用。
- 鉴权是手环（Cookie Session），每个窗口自己看一眼，没做成门卫中间件。
- 登录 ID 和聊天窗口 ID 是两套。
- IO 线程不能干等模型；等得久的菜给后厨，传菜员继续伺候别的桌。
- 没压测，不报假数字；短板自己先说。

## 第二部分：多模型接入（策略 + 工厂 + 模板注册器）

对应简历：

- 多模型对话
- 基类定义统一的对话接口，各厂商独立实现请求构建与响应解析，上层业务零感知切换

### 1. 给完全没有技术背景的人讲明白

把它想成点外卖。你只会说「我要吃这个」，不管美团、饿了么菜单长什么样。

**策略**是不同平台的点单说明书：寄到哪、单子怎么填、回执哪一行才是「做好了」。有的菜单是平铺的菜名列表（通义、豆包），有的要把菜塞进另一层盒子里（知识库 RAG）。对后厨暴露的动作一样：填单、下单、拆回执。

**工厂**是前台柜员：你报一个号（`"1"` 百炼、`"2"` 豆包、`"3"` 知识库、`"4"` 带工具的），柜员从抽屉拿出对应说明书。后厨 `AIHelper` 永远只做这三件事，不写 `if 是阿里就…… else if 是豆包就……`。

**模板注册器**：程序一启动，四本说明书自己到柜员那报到，不用在 `main` 里挨个登记。以后接微信，再写一本说明书，抽屉里加一行 `"5"` 对应微信。

### 2. 简历原句对照

### 3. 策略：先定规矩，再各家自己填

对应：`AIApps/ChatServer/include/AIUtil/AIStrategy.h`，实现在 `src/AIUtil/AIStrategy.cpp`。

| 函数 | 人话 |
|---|---|
| `getApiUrl` | 快递寄到哪 |
| `getApiKey` | 密码，构造时从环境变量读，不进仓库 |
| `getModel` | 点哪道菜，如 `qwen-plus` |
| `buildRequest` | 把内存历史填成这家要的 JSON |
| `parseResponse` | 从这家回执里抠出那句人话 |
| `isStreamSupported` | 能不能边生成边吐字。RAG 默认 false |
| `isMCPModel` | 要不要走工具调用。它是**公有字段**不是虚函数，略糙 |

四家对照：

| 编号 | 类 | 接口形态 | 流式 | 工具 |
|---|---|---|---|---|
| `"1"` | `AliyunStrategy` | OpenAI 兼容 `{model, messages}` | 是 | 否 |
| `"2"` | `DouBaoStrategy` | 同上，换 URL 和模型名 | 是 | 否 |
| `"3"` | `AliyunRAGStrategy` | `{input:{messages}, parameters}`，回执 `output.text` | 否 | 否 |
| `"4"` | `AliyunMcpStrategy` | 与 `"1"` 几乎相同，`isMCPModel=true` | 第二段可以 | 是 |

**面试一定要说的一句：** 不要吹「四家请求格式完全不同」。三家复制粘贴级相似，RAG 才是另一种盒子。策略仍然值得做：把脏格式关在子类里，明天再来一家套层 JSON 只改新文件。

RAG 的 `getModel()` 返回空串：知识库应用 API 不在请求体里带模型名，模型在百炼控制台绑在应用上。

Key：`DASHSCOPE_API_KEY` / `DOUBAO_API_KEY` / 问 RAG 还要 `Knowledge_Base_ID`（应用 ID）。平台上传文档另外要 `BAILIAN_WORKSPACE_ID` + `BAILIAN_INDEX_ID`（知识库 IndexId，不是应用 ID）。读不到对应变量，那条路径会抛异常。日志只打 Key 前 6 位。

组请求时 role 直接读 `ChatMessage.role`（`messagesToArray`），不再 `i % 2`。

### 4. 工厂 + 模板注册器

对应：`include/AIUtil/AIFactory.h`，`src/AIUtil/AIFactory.cpp`，注册语句在 `AIStrategy.cpp` 最底部。

工厂就是一张表：名字 →「怎么 new 出一个策略」。

```
create("2")
  → 查表
  → 调那条 lambda
  → make_shared<DouBaoStrategy>()   // 构造时读环境变量
```

找不到就抛 `Unknown strategy`，Handler 外层变成 400。

`instance()` 是函数里的 `static`（Meyers 单例）：第一次用才造工厂，C++11 起线程安全。

注册器：

```cpp
template<typename T>
struct StrategyRegister {
    StrategyRegister(const std::string& name) {
        StrategyFactory::instance().registerStrategy(name, [] {
            return std::make_shared<T>();
        });
    }
};

static StrategyRegister<AliyunStrategy>    regAliyun("1");
static StrategyRegister<DouBaoStrategy>    regDoubao("2");
static StrategyRegister<AliyunRAGStrategy> regAliyunRag("3");
static StrategyRegister<AliyunMcpStrategy>  regAliyunMcp("4");
```

**为什么 main 里不用登记？**  
`static` 全局对象在进 `main` 之前构造，构造函数里往表里插一条。进程一起来抽屉就是满的。

**静态初始化顺序会不会工厂还是空的？**  
工厂不是「另一个 cpp 的全局对象」，而是 `instance()` 里的局部 static，**第一次 register 时才创建**，不会用到半成品。这句被追问很好用。

运行期只读这张表，注册发生在 main 之前单线程阶段，`create` 可以不加锁。不要说支持运行时热插拔。

每次 `chat()` 都 `create` 一个新策略对象，不缓存。对象很轻（主要是一个 key 字符串）。单例缓存要考虑 Key 轮换失效；现在每次 `getenv` 能读到新值。

### 5. 上层怎么切换（基本零感知）

对应：`AIHelper.cpp` 的 `chat()`；发送在 `executeCurl()`。

```
setStrategy(StrategyFactory::instance().create(modelType));
payload = strategy->buildRequest(messages);
response = executeCurl(payload);          // URL、Bearer 都问当前 strategy
answer = strategy->parseResponse(response);
```

`executeCurl` 里不出现「阿里」「豆包」。流式失败时会拼一个假的 `choices[0].message.content`，让 `parseResponse` 不用知道刚才是流还是不流。

前端只传 `"1"`/`"2"`/`"3"`/`"4"`，默认 `"1"`。

### 8. 历史消息的 role（和「先 RAG 再总结」有关）

**现在：**

```cpp
struct ChatMessage {
    std::string role;       // "user" / "assistant" / "system"
    std::string content;
    long long   timestamp;
};
```

- `addMessage`：人写成 `"user"`，模型写成 `"assistant"`
- 启动恢复：库表 `is_user` 转成 role，不再丢掉
- `buildRequest`：`msg["role"] = m.role`
- 拉历史：`is_user = (role == "user")`，同时返回 `role` 字段

**以前：** 只存内容和时间，用下标奇偶猜。MCP 临时提示词 push 之后如果没 pop 干净，后面人/AI 会整盘错位。

**面试话术：**

> 发给厂商的 JSON 里一直有 role 字段，但以前内存没存，是用下标现场填的。现在每条消息自带 role。库里本来就有 is_user，恢复时也用上了。好处是不依赖「必须一问一答成对」，MCP 异常也不把角色搞乱，以后还能加 system。

### 9. 面试题库

#### Q1. 策略模式在你项目里解决什么问题？

**短答：**  
多家模型 URL 不同、JSON 不同、回执字段不同。不抽的话 Helper 里会堆 if。现在各家一个子类，Helper 只调统一接口。最明显的差异是知识库多套了一层 `input`。

**为什么不用一堆 if？** 加模型要改已有核心类。策略把变化关在新文件里。

---

#### Q2. 工厂干什么？和策略什么关系？

**短答：**  
策略解决「怎么聊」，工厂解决「根据一个字符串 new 出哪本策略」。前端只传 `"1"`/`"2"`，不知道类名。表：名字 → 造对象的函数。

**为什么不在工厂里写 if？** 那工厂自己变成 if 地狱。用注册表，新模型自己报到。

---

#### Q3. 「上层零感知」是什么意思？

**短答：**  
Handler 只透传 `modelType`。`executeCurl` 不出现厂商名。感知收在策略子类里。唯一破例：Helper 看 `isMCPModel` 走不走工具流程。是「不感知厂商格式」，不是一个分支都没有。

---

#### Q4. 自动注册怎么做到 main 里不用写登记？

**短答：**  
每个策略文件底下有全局 `static StrategyRegister<该类>("编号")`。进 main 前构造，往工厂表插一条。工厂是 `instance()` 里的局部 static，第一次注册才创建，没有「工厂还是空的」那种静态顺序坑。

---

#### Q5. 为什么 RAG 不能和另外三家共用一个策略、只改 URL？

**短答：**  
知识库不是 OpenAI 兼容：请求在 `input.messages`，响应在 `output.text`，URL 带应用 ID，流式格式不同所以关了 SSE。只改 URL 会把错误 JSON 寄出去。策略按行为分，不按「换个地址」分。

**那普通百炼和 MCP 为什么分成两个类？** 填单几乎一样，差在 `isMCPModel`。拆开是为了前端能单独选「带工具」。也可以一个类加开关；现在稍微重复，换的是配置清晰。

---

#### Q6. 新增一家真的只改一行吗？

**短答：**  
业务核心（Helper/Handler/curl）不用动，新增是「一个类 + 一行注册」。还要前端认编号、运维配 Key。简历强调的是核心路径闭关，不是整个产品只有一行 diff。编号用 `"1""2"` 是早期图省事，更好用 `"aliyun"` 这种名字。

---

#### Q7. 策略对象每次 chat 都新建？为什么不单例？

**短答：**  
对象很轻，每次 new 可以接受。单例要处理 Key 轮换失效；现在每次构造都 `getenv`。`create` 运行期只读表，main 前注册完，可以不加锁。热插拔再加锁。

---

#### Q8. 这是简单工厂还是抽象工厂？配配置文件不就行了？

**短答：**  
简单工厂 + 注册表。抽象工厂是一族产品一起造（按钮+输入框），我们只有一种产品 `AIStrategy`。配置文件配得出 URL，配不出「JSON 多套一层、要不要走 MCP」。格式差异是代码。URL 和模型名其实也可以再收到配置里，现在写死在子类是简化。

---

#### Q9. 密钥怎么管理？

**短答：**  
环境变量，仓库没有 Key。读不到就抛异常。日志只打前 6 位。单机演示够；生产更好走密钥服务，别和配置一起进 git。

#### Q10. 能不能一次对话里先 RAG 再换另一家模型做总结？

> RAG 结合代码的完整走读在第三部分第 12 节；这里只回答「一轮里换两家」这件事。

**短答（改完 role 之后的版本，按这个背）：**

> 现在一次 `chat()` 只 `create` 一次策略。选知识库就只打百炼应用那一次，应用自己检索并生成，把 `output.text` 当最终答案。服务端没有「先 RAG、再自动换通义/豆包写总结」的导演逻辑。
>
> 用户可以自己点两次：先选 3 问资料，再选 1 说「把上面总结成三条」。因为同一个窗口共用一份 `messages`，第二次会把上一轮带上，而且现在每条都自带 role，不会因为条数不成双就把人/AI 搞反。这是两次 HTTP、两次 chat，不是一次请求里的自动流水线。
>
> 真要做成一键流水线，应放在 Helper 这种编排层：先 `create("3")` 拿资料，再 `create("1")` 做总结。策略子类继续只负责对接一家接口，别在 RAG 类里去 new 通义，否则两家耦死，换总结模型还得改 RAG 类。

**展开（给自己看，面试别一次倒完）：**

1. `chat()` 开头 `setStrategy(create(modelType))`，这一轮用到结束。  
2. 选 `"3"` ≠ 我们代码里「检索」和「生成」两步。百炼应用接口内部才会查库+生成。  
3. MCP 两段式是**同一家**策略中间夹本地工具，不是换模型。  
4. 笨办法（两次请求）现在 role 是安全的；以前靠奇偶，两次问答碰巧还成对，MCP 一打乱就错。  
5. 导演和演员分开：Strategy 是演员，Pipeline/Helper 是导演。

**为什么不写进 `AliyunRAGStrategy`？**  
策略只该懂「怎么跟这一家说话」。子类里再调另一家，换搭配就要改演员。

#### Q12. 同一个窗口里切换模型，会影响存储吗？是不是每次只把临时 message 和用户问题交给当前模型，所以给哪家不重要？

这是自己用页面时最容易说滑的一句。面试要拆成两半：**存储跟模型解耦；推理把整段历史交给这一轮选中的那家。** 「临时 message」只存在 MCP，不是每家都有。

**短答（按这个背）：**

> 不影响存储。一个窗口就是一个 `sessionId`、一个 `AIHelper`、一份 `messages`。下拉框换模型只改这一次 HTTP 里的 `modelType`，不会新开窗口、不会另建一张表、也不会把前面的话清掉。
>
> `chat()` 开头 `create(modelType)`，这一轮用哪家策略；然后 `buildRequest(this->messages)` 把**整段正式历史**（含以前千问答过、豆包答过的）加上本轮用户问题寄出去。落库走 `addMessage`：人一句、模型一句，写的是 `role/content`，跟这轮是 `"1"` 还是 `"2"` 无关。assistant 行会多带一个 `m_curModel`，方便以后看「这句是谁答的」，不是按模型拆库。
>
> 「临时 message + 用户问题」那套只发生在 MCP（`"4"`）：内部提示词 `push` 进向量、curl 完立刻 `pop`，**不走 `addMessage`，不入库**。百炼 / 豆包 / RAG 根本没有这层。所以不是「每次都把临时句交给当前模型」；普通聊天交给模型的是整份正式 `messages`。给哪家**对存储不重要，对这一枪推理重要**——下一家会把上一家的回答当普通上下文接着看。

**展开（给自己看，面试别一次倒完）：**

1. **窗口不变。** 前端还是同一个 `currentSessionId`。`ChatSendHandler` 仍从 `chatInformation[userId][sessionId]` 拿出同一个 Helper。换的是请求体里的 `modelType`，不是 session。
2. **每轮现场选演员。** `m_curModel = modelType;` 然后 `setStrategy(create(modelType))`。策略对象不跟着窗口存一份「我永远是豆包」；下次再选百炼，再 `create("1")`。
3. **非 MCP 路径（`"1"`/`"2"`/`"3"`）。** 先 `addMessage(..., true, 用户原话)`（内存 + MQ），再 `buildRequest(this->messages)`。向量里此时已经有：更早的问答 + 刚写下的这句用户话。没有「只寄最后一句」。
4. **MCP 路径（`"4"`）。** 先把「只准输出 JSON」那种内部稿 `push_back`，第一段 curl，立刻 `pop_back`；工具跑完再 `push` 第二段提示词，curl，再 `pop`。最后才 `addMessage` 用户原话和最终人话。临时槽只活在这一次 curl 里，切走 MCP 也不会把内部稿留给豆包。细节见第三部分第 5、9 节。
5. **库表长什么样。** `pushMessageToMysql` 的 JSON 里有 `session_id`、`is_user`、`content`、`model`。`model` 取自当时的 `m_curModel`。同一 `session_id` 下可以混着 `"1"` 和 `"2"` 的 assistant 行。重启 `readDataFromMySQL` 仍按这个 session 灌回**同一份** `messages`，不会按模型拆成两个 Helper。
6. **给哪家重不重要。**  
   - 存储：不重要。同一条会话、同一张表。  
   - 推理：重要。豆包会看到百炼昨天说的那段天气长文，当成自己的上文；RAG 答完再切豆包，豆包把检索结果当普通聊天记录，它自己不会再查知识库。一般闲聊没问题。不要吹「换模型会自动隔离上下文」。
7. **和 Q10 的关系。** Q10 是「一次 `chat()` 会不会自动先 RAG 再换通义」——不会，要用户自己点两次。Q12 是「用户自己点两次、还在同一窗口，历史会不会乱、库会不会裂」——不会裂；第二次会带上第一次。role 已经写在每条消息上，不会因为换模型把人/AI 搞反。
8. **空回复也会入库。** 策略解析失败时 `answer` 可能是空串，非 MCP 仍会 `addMessage` 一条空的 assistant。页面上像没回，库里可能多一行空。这是实现细节，面试被追问可以说「失败路径没有跳过落库」。

**现场演示怎么说（对应自己切百炼再切豆包）：**

> 我刚才先用百炼问了天气，再切到豆包说你好。存储还是这个窗口。百炼那句已经在 `messages` 里了。豆包这一枪会把整段历史带上，不是只带「你好」。豆包没回，是火山那个模型 ID 404，不是换模型把库写坏了。要查天气得选 MCP，那才有临时提示词那一层。

**别说滑的三句：**

| 滑了 | 改成 |
|---|---|
| 每次只把临时 message 和用户问题交给模型 | 临时句只有 MCP 有；普通聊天交的是整段正式历史 |
| 给哪个模型不重要 | 对落库不重要；对这一轮谁来读上下文、会不会调工具，重要 |
| 换模型等于新开一场 | 还是同一个 Helper、同一份 `messages`、同一张 `chat_message` |

### 10. 可能被问住怎么圆

1. **「四家格式都不一样」** — 三家几乎一样，RAG 才不同。  
2. **「一行代码新增」** — 核心不用改；仍要写类、注册、前端、Key。  
3. **「完全零感知」** — 看了 `isMCPModel`。  
4. **`isMCPModel` 是 public 字段** — 更干净应是虚函数 `useToolCalling()`。  
5. **百炼普通 vs MCP 大量重复** — 可抽 `OpenAICompatibleStrategy`，当时赶进度没抽。  
6. **魔法数字 `"1""2""3""4"`** — 可读性差。  
7. **工厂无热更新** — 对「启动注册、只读 create」够用。  
8. **RAG `getModel()` 空** — 模型绑在应用上，不在请求体。  
9. **一次请求自动 RAG+总结** — 没做。见 Q10。不要说「现在支持多智能体流水线」。  
10. **同窗口换模型会弄丢历史 / 每次只交临时句** — 见 Q12。窗口和表都不拆；临时句只在 MCP；给哪家对存储不重要、对推理重要。

### 11. 第二部分一句话背诵卡

- 策略是说明书，工厂是报号取说明书，注册器是开机自己报到。
- Helper 只填单、寄件、拆回执；厂商 JSON 关在子类里。
- 三家 OpenAI 兼容，RAG 才套了一层；这就是为什么必须用策略，不是为了用模式而用。
- 静态 `StrategyRegister` 在 main 前插入；工厂用 Meyers 单例，没有初始化顺序坑。
- 「一行代码」指核心路径不用改，不是整个产品一行 diff。
- 一轮 chat 只用一家模型；先 RAG 再总结要导演，不能写进某个策略子类。
- 每条消息自带 role，不再用下标猜。
- 同窗口换模型不拆存储：还是一份 `messages`；`modelType` 只决定这一轮策略。临时提示词只存在 MCP，用完就 pop。给哪家对落库不重要，对这一枪上下文重要。

### 1. 给完全没有技术背景的人讲明白

模型不会查天气，也不会看你电脑上的钟。它只会说话。

所以流程像点外卖找代购：

**第一段：** 把「能买什么」（工具清单）和「顾客说了啥」塞给代购，问他：这次要不要出门、去哪家店、带什么。代购如果要出门，规定他只准写一张小纸条：`{"tool":"get_weather","args":{"city":"北京"}}`。不需要出门就直接跟人说话。

**中间：** 你自己拿着纸条去店里买（curl 打 wttr.in，或读本机时间）。模型此时不在场。

**第二段：** 把小票拍给代购：「货买回来了，用正常人话回顾客。」这时才允许打字机效果往外推字。

模型经常不听话：JSON 外包一层 markdown、夹两句闲聊、用单引号、编一个根本没有的工具名。所以纸条要四层拆，拆完还要验：工具名是不是假的、参数缺不缺、多出来的幻觉字段扔掉。验不过关，不能把内部 JSON 甩到屏幕上，要再问它一句给人看的中文。

**和 RAG 不是一回事：** RAG 是「问公司那本放在阿里云上的内部手册」；工具调用是「模型填出门条，我们去店里买」。手册检索发生在云上，出门条执行发生在我们进程里。

### 4. 第一段：只准决策，不准流式

对应：`AIHelper.cpp` 约 103–121 行；提示词在 `AIConfig::buildPrompt`；模板在 `resource/config.json`。

```
const AIConfig& config = AIConfig::instance();
string temp = config.buildPrompt(userQuestion);   // 把用户原话 + 工具清单塞进模板
messages.push_back({ "user", temp, 0 });          // 临时塞进历史，不入库
json firstResp = executeCurl(buildRequest(messages));  // 强制非流式
string aiResult = parseResponse(firstResp);
messages.pop_back();                              // 用完立刻拿掉
AIToolCall call = config.parseAIResponse(aiResult);
```

几个设计点，面试要能分开讲：

**① 提示词临时塞进历史，用完立刻 pop。**  
不走 `addMessage`，所以不入库。role 写成 `"user"`（给模型看的中间人口吻）。pop 掉是为了正式历史里只留用户原话和最终答案，不留「只输出 JSON」这种内部协议。为什么必须当场 pop，见第 11.3 节。

**② 第一段不开流式。**  
打字机一次吐一个字，你没法每吐一个字就判断「这是不是一张完整纸条」。必须等整段才能阅卷。第二段已经是给人看的句子，可以流式。

**③ 配置是单例。**  
`AIConfig::instance()` + `call_once` 加载。工具清单不会每句话变一次，不必每次打开 `config.json`、不必每次编译正则。加载失败会打 FATAL 日志，工具调用等于停用，不会把请求直接打挂。

**④ `buildPrompt` 用普通字符串替换 `{user_input}` / `{tool_list}`，不用 `regex_replace`。**  
替换串里 `$` 在正则里是特殊字符，用户输入 `$&` 会被当成「整段匹配」展开，等于提示词注入。普通 `find` + `replace` 没有这个坑。

提示词里写死了：要调工具就只输出一个 JSON，禁止 markdown，工具名必须从清单里抄；不需要就直接说人话。

### 5. 阅卷：四层解析 + 一道闸

对应：`AIConfig::parseAIResponse` / `validateToolCall`，`AIConfig.cpp`。

`parseAIResponse` 不是「解析成功就调工具」。流程是：尽量抠出 JSON 候选 → 每个候选过校验 → 第一个合格的才算调工具。

```
L0 整段就是 JSON            模型听话时走这里（parseStage=direct）
L1 剥掉 ```json ... ```     模型爱套代码块（code_fence）
L2 从闲聊里括号配对抠 {...}  「好的，查一下：{...} 稍等」（brace_scan）
L3 正则硬抠 tool/args       单引号、中文冒号、键没加引号（regex_field）
     ↑ 只当前三层一个候选都没有时才启用
```

L2 必须认字符串和转义：城市名叫 `北}京` 时，不能看到 `}` 就截断。花括号没配平（输出被截断）这一层失败。

L3 很松。用户正常说「用 tool: '锤子' 钉钉子」也可能被当成调工具，所以**前面还有候选时绝不走 L3**。中文冒号用 `(?::|：)` 分支而不是字符类 `[:：]`：`std::regex` 按字节匹配，全角冒号是三个 UTF-8 字节，塞进字符类会对不上。这是面试可以顺口提的实现细节，别当核心卖点。

校验 `validateToolCall` 过五关：

1. 有没有 `tool` 字符串。没有 `tool` 字段：当普通聊天，`rejectReason` 为空（模型可能回了一段普通 JSON 数据，不是工具调用）  
2. 名字在不在 `config.json` 白名单（防 `get_stock_price` 幻觉）  
3. `args` 若是字符串再解析一层（模型有时写成 `"args": "{\"city\":\"北京\"}"`）  
4. 声明过的参数必须有且非空；值统一收成字符串  
5. 只留下声明过的键，多出来的 `unit` 扔掉，不传给工具  

过不了：`isToolCall=false`，带上 `rejectReason`。  
`parseStage` 和 `rejectReason` 是给线上排查用的：这次是哪一层看懂的、为什么没调。

**解析解决「看懂」，校验解决「能不能执行」。** 面试就用这句。

### 6. 不调工具 vs 想调但没过关（「再打一轮普通人话」）

对应：`AIHelper.cpp` 约 123–150 行。这是学完模块后追问最多的一段，按下面背。

第一段模型已经回过一次了，结果在 `aiResult`。阅卷后出现两种「不调工具」，**别混**：

| | 含义 | 给用户看什么 | 还要不要再问模型 |
|---|---|---|---|
| `isToolCall=false` 且 `rejectReason` **空** | 模型就是在跟人聊天，比如回「你好呀」 | 第一段原文 | 不用 |
| `isToolCall=false` 且 `rejectReason` **非空** | 想调工具但纸条不合格（假工具名、缺参数） | **不能**把内部 JSON 甩出去 | **再 curl 一次，求一句中文** |

第二种代码在干什么（人话）：

1. 先把**用户原话**（不是「只准输出 JSON」那套内部提示词）临时推进 `messages`  
2. **再 curl 一次同一家模型**：这次历史里没有「你必须输出工具 JSON」的紧箍咒，等于普通聊天  
3. 模型这次通常会说「我这边查不了股价」这种人话  
4. `pop_back` 把刚才那句临时原话拿掉（因为下面 `addMessage` 会正式再记一遍）  
5. `addMessage` 用户原话 + `addMessage` 这句人话，返回给浏览器  

**「再打一轮普通人话」= 再请求一次大模型，目的是要一句给人看的中文，不是再试一次调工具。**

和真正的「第二段」对比：

| | 校验失败这条分支 | 真调了工具之后的第二段 |
|---|---|---|
| 有没有跑天气/时间 | 没有 | 有 |
| 再问模型时带什么 | 只有用户原话 | 原话 + 工具小票 |
| 目的 | 把内部 JSON 翻译成人话 | 根据真实结果回答 |

重试也失败（curl 抛异常或空串）：沿用第一段原文。这时原文可能仍是 JSON，是残余风险，面试承认。

### 7. 真调工具：本地执行，再二次推理

对应：`AIHelper.cpp` 约 153–215 行；执行在 `AIToolRegistry.cpp`。

```
static const AIToolRegistry registry;          // 注册表只读，构造一次复用
toolResult = registry.invoke(call.toolName, call.args);  // 本地跑，不再问模型
secondPrompt = config.buildToolResultPrompt(...);        // 人话拼小票
messages.push_back({ "user", secondPrompt, 0 });         // 临时
finalAnswer = executeCurl(...);                          // 第二段可以流式
messages.pop_back();
addMessage(用户原话);
addMessage(最终人话);
```

- `invoke` 查表调 C++ 函数，**不是再问模型「请你假装查了天气」**  
- `get_weather`：curl `https://wttr.in/城市?format=3&lang=zh`，城市做 URL 编码，5 秒超时。不是把模型给的任意 URL 拿去乱请求  
- `get_time`：本机 `localtime`，没有参数。标准 `localtime` 有静态缓冲，多线程 theoretically 不安全，更严谨用 `localtime_r`。体量小，面试别装没看见  
- 第二段提示词是人话拼出来的：「用户说了啥、刚调了哪个工具、返回如下，请用自然语言回答。」  
- 临时提示词仍然 pop，入库的只有原话和最终答案  
- 一轮最多调 **一次** 工具，没有「根据结果再决定调第二次」的 ReAct 循环  
- `invoke` 抛异常：返回「工具调用失败」加原因，历史里记下，**不再二次推理**

`registry` 做成 `static const`：每次请求 new 一张 hash 表纯属浪费，工具函数不会变。

### 9. 一次请求怎么走（画图用）

用户选模型 4，问「北京天气怎么样」。窗口之前是空的。

```
chat(modelType="4")
  │
  ├─ 拼第一段提示词（工具清单 + 用户原话）临时推进 messages
  ├─ curl 百炼（非流式）→ 模型返回例如：
  │     {"tool":"get_weather","args":{"city":"北京"}}
  ├─ pop 临时提示词          ← messages 又干净了
  ├─ parseAIResponse
  │     L0 直接就是 JSON → validate 白名单 + city 齐全 → isToolCall=true
  │
  ├─ registry.invoke("get_weather", {city:北京})
  │     curl wttr.in → {"city":"北京","weather":"北京: 晴 22°C"}
  │
  ├─ 拼第二段提示词（原话 + 工具结果）临时推进 messages
  ├─ curl 百炼（可流式）→ 「今天北京晴，大约 22 度。」
  ├─ pop 临时提示词
  └─ addMessage 正式历史只留下：

        （同时丢进 MQ，准备写 MySQL）
```

另外三条岔路：

- 模型第一段说人话、不调工具：解析当文本，直接 `addMessage` 返回，不再 curl  
- 模型编了个假工具名：校验拒绝 → 再问一轮人话 → 给用户看人话，不看 JSON  
- 模型把 JSON 包在 \`\`\`json 里：L1 剥开再校验，日志会打 `recovered by fallback, stage=code_fence`

### 11. 学完后追问过的易混点（按讨论原样整理）

#### 11.1 `addMessage` 干什么（不是往 map 里塞）

窗口对象 `AIHelper` 早就在 `chatInformation[userId][sessionId]` 这份 map 里了。那是 Handler 里 `getOrCreateChatHelper` 做的。`addMessage` **不创建窗口**，只给**当前这个窗口的聊天记录**追加一条。

```
void AIHelper::addMessage(...) {
    messages.push_back({ roleFromIsUser(is_user), userInput, ms });  // ① 内存
    pushMessageToMysql(...);                                          // ② 丢进 MQ
}
```

两步：

- **① 内存：** 写进这个 `AIHelper` 自己的 `messages` 向量。下一轮组请求会把这些话带给模型。`true` = 用户 → role `"user"`，`false` = AI → `"assistant"`  
- **② 异步落库：** `pushMessageToMysql` 组一份 JSON，`publish("sql_queue")`。IO 线程不等 MySQL。后台消费线程拿去 INSERT。模块 4 会细讲队列

和临时 `messages.push_back` + `pop_back` 的对比：

| | 临时 `push_back` | `addMessage` |
|---|---|---|
| 干什么 | 只为了**这一次** curl 让模型看见某段话 | 正式记入对话 |
| 会不会 pop | 会，用完扔掉 | 不会 |
| 会不会进 MySQL | 不会 | 会（经 MQ） |
| 例子 | 内部提示词、校验失败时为了再问一次而临时塞的原话 | 「北京天气怎么样」+ 最终回答 |

map 只在「第一次找到/创建这个窗口」时动。不要说 `addMessage` 往 `chatInformation` 里插。

---

#### 11.2 `chatInformation` 和 MySQL：谁扛上下文

当时理解里有两处要改说法。

**对的部分：**

- **真正扛上下文的是内存。** 热路径组请求不查库。下一轮带给模型的就是这个 Helper 的 `messages`  
- **MySQL 是持久化。** 重启后 `readDataFromMySQL()` 按时间把表灌回各个 Helper 的 `messages`。库挂了、还没来得及写入的那几句，内存里有、重启会丢  
- **给用户看的、入库的，是原话 + 最终答案。** 内部那套「只输出 JSON」、工具小票提示词，不会进库  

**需要改的两处：**

**① `chatInformation` 里存的不是一条条 message，是一个个窗口。**

```
chatInformation
  userId 100
    sessionId "aaa" → AIHelper   ← 窗口对象
                 └── messages: [ {user, "北京天气"}, {assistant, "晴 22 度"} ]
    sessionId "bbb" → 另一个 AIHelper
```

类型是 `unordered_map<int, unordered_map<string, shared_ptr<AIHelper>>>`。message 挂在 Helper 上，不是直接摊在 map 里。

**② 不是「先随便塞，再删成和 MySQL 一样」。**

两条路从一开始就分开：

| | 临时 `push_back` + `pop_back` | `addMessage` |
|---|---|---|
| 谁看得见 | 只为这一次 curl | 内存正式历史 |
| 会不会进 MySQL | 不会 | 会（经 MQ 异步 INSERT） |
| 何时消失 | **当场 pop**，不是事后对照库再删 | 一直留着，直到进程退出 |

所以内存正式历史和库表**本来就该是同一批内容**：用户问题 + AI 最终回答（以及校验失败时那句人话、工具失败时的错误句）。不是 MySQL 更少、内存再削一刀去对齐。

时序是：**先写内存，再丢 MQ。** 可能内存已经有了、库还差几百毫秒。运行时以内存为准；对齐发生在下次启动灌库，不是边聊边拿库来裁内存。

**一句话背：** 窗口在 `chatInformation`，对话在 Helper 的 `messages`；内部提示词用完就 pop，从不入库；MySQL 存的是正式对话，用来重启恢复；聊天时上下文只看内存。

---

#### 11.3 为什么需要当场 pop（数组怎么变）

因为 **`buildRequest` 会把当前 `messages` 里每一条都寄给模型**。临时提示词只该存在「这一次 curl」期间；留下去，下一轮、拉历史、入库都会把它当成正经对话。

用一次「北京天气」把数组画完。假设这窗口之前是空的。

**第一段：塞提示词 → 问模型 → 立刻 pop**

```
① push 内部提示词之后
messages =
  [ {user, "我是中间人……用户说：北京天气怎么样 工具: get_weather…"} ]

② executeCurl：模型看见的就是上面这一份
   它回 {"tool":"get_weather","args":{"city":"北京"}}

③ pop_back，提示词消失
messages = []          ← 又干净了
```

**为什么必须在这里 pop，不能等最后再删？**

后面还有第二段 curl、可能还有「校验失败再问一次」。那些请求也会把**整份** `messages` 发出去。如果内部那句「只准输出 JSON」还在：

- 第二段你其实想让它「根据小票说人话」，它却还被第一段的紧箍咒绑着，可能继续只吐 JSON  
- 校验失败那次你想问一句普通问题，它仍会看到工具协议  

所以：**每次 curl 用完就 pop，保证下一次 curl 看到的历史里没有上一次的内部话术。**

**真调了工具：再塞第二段 → 再问 → 再 pop → 再正式记账**

```
④ 本地查完天气。push 第二段提示词
messages =
  [ {user, "用户说北京天气。我调了 get_weather，返回晴 22°C，请用自然语言回答"} ]

⑤ 第二次 curl（可以流式）：模型看见的只有这一句 + 以前的正式历史
   它回「今天北京晴，大约 22 度。」

⑥ pop 第二段提示词
messages = []

⑦ addMessage 用户原话 + addMessage 最终答案
messages =
  [ {user, "北京天气怎么样"},
    {assistant, "今天北京晴，大约 22 度。"} ]
```

这时才和 MySQL 要存的东西一致。拉历史、下一轮对话，模型看到的也是这两句，**看不到**「只输出 JSON」和「工具返回如下」。

若 **⑥ 不 pop 就 ⑦**：

```
messages =
  [ {user, "……请用自然语言回答……"},   ← 内部稿，前端也会当一句聊天
    {user, "北京天气怎么样"},
    {assistant, "今天北京晴…"} ]
```

用户刷新能看见内部稿；下一轮模型会把内部稿当成上下文；token 白白变长。`addMessage` 还会再写库，库里也会出现内部稿。当场 pop 就是为了 **永远不要走到这一步**。

**校验失败那条：同样「用完就扔」**

第一段已经 pop 过，`messages` 是空的（或只有更早的正式历史）。

```
push 用户原话（没有工具协议）
  curl 再问一次 → 要一句中文
pop 这句原话          ← 否则下面 addMessage 会再记一遍，变成连续两条一样的 user
addMessage 原话
addMessage 人话
```

这里的 pop 还有第二层意思：**避免同一句用户话在向量里出现两次。** 临时 push 只为了这次 curl 带上它；正式记录交给 `addMessage`（顺带落库）。

**一张总表：**

```
正式历史（messages 里长期留着的）     临时槽（curl 前 push，curl 后 pop）
────────────────────────────────     ────────────────────────────────
用户原话、AI 最终答案                第一段：带工具清单的内部提示词
下一轮还要带给模型                   校验失败：仅原话、为了再问一次人话
会进 MySQL                           第二段：带工具小票的内部提示词
                                     不进 MySQL，前端也不该看见
```

**当场 pop = 这次寄给模型的信封用完就拆掉，别混进对话本。** 不是和 MySQL 对账之后再删，是根本不让它成为正式历史。

### 12. RAG 结合代码（模型 `"3"`，不是工具调用）

模块 3 讲工具时容易以为 RAG 也在两段式里。**不是。** RAG 是模块 2 的第三条策略，选 `"3"` 根本不会进 `isMCPModel` 分支。这里按后来「结合代码把 RAG 讲一遍」的口径写完整，面试可以单独拿出来讲。

#### 12.1 人话：RAG 在这儿指什么

教科书 RAG：本地切文档 → 向量库 → 问句检索出几段 → 和问题一起送给模型。

你们：**知识库是一份共享库**，绑在一个应用 ID 上。问的时候代码只做一件事：把聊天记录 POST 到

`https://dashscope.aliyuncs.com/api/v1/apps/{Knowledge_Base_ID}/completion`

云端自己搜文档、自己生成。你们拿到的是已经写好的答案 `output.text`。

灌库后来加了一条独立链路：`POST /kb/upload` → `BailianKnowledgeClient` 调百炼数据面（租约 → PUT 文件 → AddFile → 追加索引）。**不是**在平台上做 embedding。文档进入的是同一份共享库，所有人选「百炼 RAG」都能问到。索引是异步的，接口提交任务就返回 `jobId`，前端轮询 `/kb/job-status`。`/upload` 仍是识图，别混。

所以简历上的「知识库检索增强」，检索发生在**厂商侧**，不在 `CppAIService` 进程里。仓库里没有 embedding、没有 Faiss/Milvus。**面试别说「我实现了向量检索」。**

#### 12.2 从点击到答案

前端 `modelType: "3"`，和普通聊天同一个接口 `POST /chat/send`。

`chat()` 里 `create("3")` → `AliyunRAGStrategy`。构造时读 `DASHSCOPE_API_KEY`，**`isMCPModel = false`**。

因此走和百炼/豆包相同的「问一次就返回」：

```
addMessage(..., true, userQuestion);       // 先把用户问题写入正式历史
payload = strategy->buildRequest(messages);
response = executeCurl(payload);           // RAG 通常走这里：非流式
answer = strategy->parseResponse(response);
addMessage(..., false, answer);
return answer;
```

没有 push/pop 内部提示词，没有 `parseAIResponse`，没有 `registry.invoke`。就是：记账 → 按 RAG 格式填单 → curl → 拆答案 → 记账。

`executeCurl` 仍然问 `strategy->getApiUrl()` / `getApiKey()`，所以 Helper 不知道这是知识库。这就是策略模式的好处。

#### 12.3 和普通百炼差在哪三处（全在 `AliyunRAGStrategy`）

类声明：`AIStrategy.h` 约 101–121 行。实现：`AIStrategy.cpp` 约 82–113 行。注册：`regAliyunRag("3")`。

**① 寄到哪：应用接口，不是 chat/completions**

```
getApiUrl() {
    id = getenv("Knowledge_Base_ID");   // 没有就抛异常
    return "https://dashscope.aliyuncs.com/api/v1/apps/" + id + "/completion";
}
```

环境变量缺了，选 3 会直接抛错。换一份知识库：问改 `Knowledge_Base_ID`，灌库改 `BAILIAN_INDEX_ID`，两边要指向同一套百炼配置。

**② 填单：多套一层 `input`，没有 `model` 字段**

```
getModel() { return ""; }    // 模型在控制台绑在应用上，不写进请求体

buildRequest(...) {
    payload["input"]["messages"] = messagesToArray(messages);  // role 仍读 ChatMessage
    payload["parameters"] = {};
}
```

普通百炼是 `{ "model":"qwen-plus", "messages":[...] }`。  
RAG 是 `{ "input": { "messages":[...] }, "parameters":{} }`。

这就是第二部分 Q5 说「不能只改 URL」的原因：盒子形状不同。

**③ 拆回执：`output.text`，不是 `choices[0].message.content`**

```
if (response.contains("output") && response["output"].contains("text"))
    return response["output"]["text"];
```

#### 12.4 为什么没有打字机效果

`AIStrategy` 里 `isStreamSupported()` 默认 `false`。百炼/豆包/MCP 子类 override 成 `true`，**RAG 没有 override**。

于是 Handler 里：

```
useStream = 前端想流式 && strategy->isStreamSupported() && 有回调
          = true && false && ... → false
```

走一次性 JSON，不走 SSE。注释写了：RAG 接口流式格式不同，本期不支持。选知识库时，用户会等整段答案一起出来。

#### 12.5 和 MCP / 普通对话对比（一张表背完）

```
选 "1" 普通百炼
  一次 curl → chat/completions → choices[].content
  模型只靠对话历史，没有你们的文档

选 "3" RAG
  一次 curl → apps/{id}/completion → output.text
  云端先搜知识库再生成
  你们进程里没有检索代码

选 "4" MCP
  Helper 两段式 + 本地 get_weather/get_time
  和知识库无关
```

多轮：RAG 同样用这个窗口的 `messages`。每次 `buildRequest` 会带上之前的问答，云端应用能接着聊。检索仍在云端，不是你们本地缓存文档。

#### 12.6 RAG 面试话术（直接背）

> RAG 我接的是百炼应用 API，不是自研向量库。问：前端传 3，工厂给出 AliyunRAGStrategy，请求体 input.messages，URL 带应用 ID，回执 output.text。灌库：菜单上传走 POST /kb/upload，BailianKnowledgeClient 调数据面把文件追加进同一份共享 Index，索引异步，用 jobId 轮询。检索和生成都在云上。流式没做，因为问的接口格式和 OpenAI delta 不一样。`/upload` 是识图，别混。

被问「为什么不自己做检索」：课程体量下用托管知识库更快；自己做要切分、embedding、召回、重排，那是另一套系统。

被问「知识库内容在哪」：在百炼那一份共享库。可以在控制台传，也可以在我们平台 `/kb/upload` 同步上去。聊天用 `Knowledge_Base_ID`（应用），灌库用 `BAILIAN_INDEX_ID`（知识库）。不是按用户隔离的。

被问「一次对话先 RAG 再换另一家总结」：见第二部分 Q10。现在一次 `chat()` 只 create 一次策略。用户可以自己点两次（先 3 再 1），同一窗口共用 `messages` 且每条自带 role。真要一键流水线，导演放 Helper，别在 RAG 类里去 new 通义。

### 13. 面试题库

下面包含模块 3 当时出的题，以及后来追问过的题。短答按「面试回答」说；括号里是给自己看的。

---

#### Q1. 模型不会上网，你怎么让它查天气？

**短答：**  
不让它上网。第一段只让它决定「调不调、调哪个、参数」；我们在服务器上执行工具；第二段把结果给它，让它组织人话。模型始终只负责说话和填表。

**为什么不让模型直接编一个天气？** 会一本正经胡说。工具结果是真实请求来的，模型只负责翻译成口语。

---

#### Q2. 简历写参考 MCP，你实现的是标准 MCP 吗？

**短答：**  
不是。借的是「工具清单 + 结构化调用 + 执行后再生成」这个思想。没有 MCP 的 JSON-RPC、没有官方传输。自研两段式，协议就是一小段 `{tool, args}`。类名带 Mcp 是命名夸张，面试主动说清楚。

**为什么不接官方 MCP / 厂商 function calling？** 当时要的是可控、轻量、能讲清自己的解析和校验。厂商 function calling 更稳，但协议细节被云包掉，简历那句「自研两段式」就没了。体量大了应迁到官方 function calling，自研解析当降级。

---

#### Q3. 为什么要两段，不能一段搞定？

**短答：**  
一段里模型既要决定调工具又要编最终答案，它没有真实工具结果，只能猜。两段把「决策」和「组织语言」切开，中间插入一次确定性的本地执行。代价是多一次模型调用、多花 token、第一段还不能流式，首字更慢。

---

#### Q4. 第一段为什么不能流式？

**短答：**  
流式是边生成边往浏览器推。第一段要的是一张完整的「调工具纸条」或完整人话，半截 JSON 无法校验。所以第一段等齐。第二段已经是给人看的句子，可以流式。

**那用户第一段要等很久怎么办？** SSE 心跳还在（第一部分），避免代理把连接掐掉。体验上第一段确实是静默等待。

---

#### Q5. 模型输出不规范怎么解析？为什么还要校验？

**短答：**  
四层：整段 JSON → 剥代码块 → 从闲聊里配对花括号 → 语法都坏了才正则抠字段。抠出来只说明「长得像」，还要过白名单、必填参数、丢掉多余字段。解析解决「看懂」，校验解决「能不能执行」。

**正则为什么放最后？** 太松，闲聊里出现 `tool: 'xx'` 会误判。前三层有候选就不用它。

**解析成功但工具名是编的？** 白名单拦住，当「想调没调成」，再打一轮人话，不把内部 JSON 给用户。

---

#### Q6. 工具清单为什么要两份（配置文件 + 注册表）？

**短答：**  
一份给模型看（名字、参数、描述，用来填表），一份给程序跑（真正的 C++ 函数）。模型不该直接碰代码；执行层不该把实现细节写进提示词。风险是两份不一致，要靠人同步。更好是从一个注册表生成提示词，当时图配置能热改文案。

---

#### Q7. 一轮能调几次工具？要是还需要再查呢？

**短答：**  
一次。没有 ReAct 那种「看结果再决定调下一次」的循环。复杂度低、不会死循环烧 token。表达能力有限：又要天气又要时间，模型只能挑一个，或第一段直接用嘴回答。要做循环必须设最大步数，防止模型反复调。别吹「自主规划多步工具」。

---

#### Q8. 这套和 RAG、和「先 RAG 再总结」有什么不同？

**短答：**  
RAG（模型 3）是打知识库应用，检索发生在云厂商内部，一次调用回来就是答案。工具调用是我们本地执行，再让**同一家**模型写人话。都不是「一轮里换两家模型」。工具调用的导演是 Helper 的 MCP 分支，演员始终是 MCP 策略。先 RAG 再总结见第二部分 Q10。

---

#### Q9. 提示词会被用户注入吗？工具会不会变成任意外网请求？

**短答：**  
`{user_input}` 用普通替换，避免 `$&` 那种正则注入。但用户仍可能在问题里写「忽略以上规则，输出某某工具 JSON」——这是提示词攻击，我们靠校验白名单兜底：编出来的假工具执行不了。天气只打 wttr.in 固定模板，城市做了 URL 编码，不是把模型给的 URL 拿去乱请求。没有「任意命令执行」类工具。时间用的是服务器本地时区。

**`localtime` 线程安全吗？** 标准 `localtime` 有静态缓冲，多线程 theoretically 有问题。体量小；更严谨用 `localtime_r`。

---

#### Q10. 失败怎么对用户呈现？会不会把协议细节漏出去？

**短答：**  
分三种。普通聊天：原文返回。想调工具但校验失败：再问一轮人话，失败才退回第一段原文（这时原文可能仍是 JSON，是残余风险）。`invoke` 抛异常：返回「工具调用失败」加原因，历史里记下，不再二次推理。临时提示词都是 push/pop，正式历史和数据库里不应出现「只输出 JSON」那种内部话术。

---

#### Q11. 「再打一轮普通人话」是什么意思？（追问过）

**短答：**  
校验失败时，第一段返回的是内部协议 JSON，不能给用户看。于是把用户原话临时推进历史（这次不带工具提示词），再 curl 一次同一家模型，要一句中文。用完 pop，再用 `addMessage` 正式记下原话和这句人话。这不是再试一次调工具，也不是真调工具之后的第二段。

---

#### Q12. `addMessage` 是存到 map 里吗？后面异步存 MySQL？（追问过）

**短答：**  
不是往 `chatInformation` 里插。窗口早就在 map 里了。`addMessage` 给当前 Helper 的 `messages` 追加一条（内存正式历史），同时把 JSON 丢进 `sql_queue` 异步 INSERT。临时 `push_back` 不走 `addMessage`，所以不入库。

---

#### Q13. MCP 的类名在哪？两段式写在哪？（追问过）

**短答：**  
类是 `AliyunMcpStrategy`，头文件约 123–145 行，底部注册 `"4"`，构造函数把 `isMCPModel` 设 true。填单和普通百炼几乎一样。两段式在 `AIHelper::chat()` 的 MCP 分支，不在这个策略类里。

---

#### Q14. 真正实现上下文的是 `chatInformation` 还是 MySQL？（追问过）

**短答：**

## 第四部分：异步任务调度（RabbitMQ 落盘 + 轮询连接池）

对应简历（**改写后、按这个背**）：

> 异步任务调度：对话记录经 RabbitMQ 异步落盘，流式请求交由 Worker 池执行，避免 IO 线程阻塞。

旧简历曾写成「RabbitMQ 构建异步推理流水线，将 AI 对话与图像识别解耦至后台 Worker 池」。**按代码对不上**，下面「怎么圆」和「要不要真做成推理队列」整节都为这句话服务。

---

### 1. 给完全没有技术背景的人讲明白

聊天时有两件快慢差很多的事：

1. **给用户回话** —— 已经等过大模型，答案在内存里，浏览器可以先拿到。  
2. **把这句话记进数据库** —— 给重启后恢复用。磁盘 IO，可能几毫秒，堵车时更久。

如果在 IO 线程里同步 `INSERT`：大模型已经堵过一次，再堵一次数据库。数据库一抖，整条连接上别的请求也跟着等。

所以改成：**内存先记（`addMessage`），纸条丢进信箱（RabbitMQ `sql_queue`），自己去给用户回话。** 后院 2 个人专门拆信、写库。信箱还能暂存：写入突然变慢，纸条先堆在队列里，聊天线程不用停。

**轮询连接池：** 往信箱塞纸条的人不止一个（4 个 IO 线程 + 8 个流式 worker 都可能 `publish`）。如果全员抢同一根管子、同一把锁，又变成排队。于是准备 5 根管子，大家按 1、2、3、4、5、1、2……轮着塞，每根管子自己一把锁。

**另一件「别堵 IO」的事，不是 MQ：** 流式对话要卡在 curl 上等模型。这事丢给 `StreamWorkerPool`（8 个普通 C++ 线程）。和 RabbitMQ 无关。简历里「Worker 池」指这个，不是消费 `sql_queue` 的那 2 个人。

### 3. 代码怎么串起来

#### 3.1 什么时候往队列里塞

只有正式对话走 `addMessage` 才会 publish。临时提示词 push/pop 不走这里（第三部分）。

```
addMessage:
  messages.push_back(...)     // 内存立刻有，热路径上下文看这个
  pushMessageToMysql(...)     // 组 JSON，publish("sql_queue")
```

队列里是结构化 JSON，**不再拼 SQL**（改造前 `sessionId` 来自请求体直接拼进语句，有注入）。字段包括 `type=chat_message`（预留以后同一队列扩别的写）、userId、内容、ts、model、token。token 只记在 AI 那一行。

HTTP 到这里就可以返回。库写没写完，用户已经看到答案。

对应：`AIHelper.cpp` 的 `addMessage` / `pushMessageToMysql`。

#### 3.2 发布端：5 根管子轮询

`MQManager` Meyers 单例。第一次 `instance()` 造 5 个 `MQConn`：每个一个 AMQP `Channel`（`localhost:5672` / `guest`）+ 一把自己的 `mutex`。SimpleAmqpClient 的 Channel **不是线程安全的**，必须每根加锁。

```
index = counter_.fetch_add(1) % 5;   // 无锁选号
锁住这一根的 mutex
BasicPublish("", "sql_queue", msg)   // 空 exchange = 默认交换机，按队列名直投
```

单连接 = 所有 publish 串行。5 根管子 5 把锁，冲突摊开。**5 是经验值，不是压测结论。**

发布 fire-and-forget：没有 publisher confirm。进程崩在 publish 返回、broker 还没落盘之间，纸条可能丢。

对应：`MQManager.cpp` 的 `publish`。

#### 3.3 消费端：另外 2 个人拆信

和发布池 **不是同一批连接**。`main()` 顺序：ChatServer 起来 → sleep 2s → 从 MySQL 灌回内存 → `RabbitMQThreadPool(..., 2, executeMysql).start()` → 再 `server.start()` 接客。先开消费者，队列 `DeclareQueue` 成 durable。

每个 worker：自己 `Channel::Create`；`BasicConsume(..., exclusive=false)`（曾经 exclusive，两线程抢同一队列 403）；`BasicQos(..., 1)` 一次只预取 1 条；循环里 `BasicConsumeMessage` 最多等 500ms 以便看 `stop_`；**先 `executeMysql` 再 `BasicAck`**。

Qos(1) 人话：老板一次只给每个伙计一张单，干完再拿下一张，避免一个人囤一堆、另一个闲着。

对应：`MQManager.cpp` 的 `worker`；`main.cpp` 启动。

#### 3.4 真正写库

`executeMysql`：JSON 解析失败则当旧版裸 SQL 执行（升级期兼容）。成功则 `INSERT ... VALUES (?,?,...)` 九个字段预处理绑定。异常 catch 住打日志 **不往外抛**。

结合「先 handler 再 ack」：

| 情况 | ack？ | 消息命运 |
|---|---|---|
| INSERT 成功 | 是 | 正常消失 |
| INSERT 失败但被 catch | **仍 ack** | **这条丢了**（队列不被脏数据卡死） |
| 若没 catch、抛出去 | 否 | 会重投，可能死循环 |

写库走另一套池：`MysqlUtil` → `DbConnectionPool`（启动时 5 个 MySQL 连接）。登录/注册等接口也用这池，但是同步的，不走 RabbitMQ。

### 4. 别把三套「池」讲混（追问过：Worker 池是什么）

| 名字 | 几个 | 干什么 | 是不是 MQ |
|---|---|---|---|
| Muduo IO 线程 | 1 主 + 4 IO | 网络收发 | 否 |
| **StreamWorkerPool（简历「Worker 池」）** | **8** | **流式对话里去 curl 模型** | 否 |
| MQ 发布池 | 5 个 channel | 多线程同时塞队列 | 是 |
| MQ 消费线程 | 2 | 拆信写 MySQL | 是 |
| MySQL 连接池 | 5 | 真正执行 SQL | 否 |

流式推理 **没有第二个专用池**。RAG 不支持流式，不进 StreamWorkerPool；识图也不进。

`ChatSendHandler`：流式时 IO 线程写完 SSE 头，`submit` 给池子就 return；`chat()` 在 worker 里跑。

### 5. 一次请求怎么走（画图用）

流式对话：

```
IO 线程：鉴权、找 Helper、写 SSE 头、submit，立刻去伺候别的连接
        │
        ▼
StreamWorkerPool：curl 大模型
        ├─ addMessage(用户原话) → 内存 + publish
        ├─ addMessage(AI 答案)  → 内存 + publish
        └─ SSE 推完 [DONE]

同时或稍后：
RabbitMQ 2 消费者之一拿到 JSON → MySQL 池借连接 → 预处理 INSERT → ack
```

非流式（RAG 等）：`chat()` 仍在 **IO 线程**，写库照样只 publish。识图：推理仍同步；分类结果后来也走同一条 `sql_queue` 落 `image_result` 表（见第六部分），**不是**把 ONNX 丢进队列。

和第三部分的关系：

```
内存 messages     = 当下上下文（热）
sql_queue         = 正在路上的持久化
MySQL chat_message = 已经落地的副本（冷，给重启）
```

可能内存有了、库还差几百毫秒。`addMessage` 是先内存后 publish，**没有把两步做成事务**。

### 6. 讨论过：简历那句要不要按字面做？DeepSeek 是不是同步等？

**结论：按字面把对话和识图都丢进 MQ 推理队列，可行，但对这种聊天站几乎没意义。**

先拆三层「异步」：

| 谁在问 | 实际是什么 |
|---|---|
| 用户 | 同步等待**这一轮**答案（有打字机） |
| 浏览器 | 一次长连接，流式收（SSE / WebSocket） |
| 服务器 | **不该**用 IO 线程去干等 curl / ONNX |

DeepSeek / ChatGPT 网页：**用户感受就是同步等这一轮**。实现一般是连接不关、边生成边推字，**不是**「立刻 202 + taskId + 前端轮询」。轮询是 Midjourney、长视频、离线批量那种。聊天做成交作业，首字更慢，体验更差。

「聊天页就该同步阻塞」如果指**用户等这一轮** → 对。如果指 **IO 线程里死等模型** → 应拆开。流式已经丢进 StreamWorkerPool，这才是正确位置。

真值得做的、不必改用户体验：

1. 对话继续长连接流式；非流式（RAG）也可以丢进计算池，**请求仍等这次结束再返回**，只是别占 EventLoop。  
2. 识图从 IO 线程拿开进 Worker；HTTP 照样等这次推理完再给 JSON。识图没有打字机需求，比对话改 MQ 更有意义。  

`202 + taskId` 适合：几十秒到几分钟、用户可离开页面、推理机和接入机分离、要限流重试。你们对话几秒、识图更短、单进程、还要把答案立刻写进 `messages`，再上 `ai_task_queue` 是为简历字面。

面试被问「为什么没做成全异步推理」：

> 对话产品要的是这一轮连着等、能流式出字。我把阻塞从 IO 线程卸到 StreamWorkerPool，队列留给落库。识图更适合进计算池，但交互仍是一次请求等一次结果。taskId 轮询是长任务模型，不是 DeepSeek 这种聊天页。

### 8. 面试题库

#### Q1. 为什么写库要异步？聊天不是已经等了好几秒模型吗？

模型那几秒不该再叠一次磁盘。更重要的是解耦和削峰：MySQL 抖动时聊天仍能返回（答案已在内存）；写入洪峰先堆队列。代价：重启可能少最后几条。同一进程内拉历史走内存，刷新还在；换机器/重启才暴露未落地的。

#### Q2. 队列里传什么？为什么不传 SQL？

结构化 JSON，INSERT 写死在消费端，预处理占位符。以前拼 SQL 有注入。`type` 预留扩写操作，目前只有 `chat_message`。

#### Q3. 发布连接池为什么轮询？5 怎么来的？

Channel 非线程安全，每连接一把锁。单连接 = publish 串行。原子 `fetch_add` 选号。5 是经验值。

#### Q4. 消费为什么 Qos(1)？为什么不能 exclusive？

公平分发，每人最多一条未 ack。exclusive 表示队列只许一个消费者，两个 worker 会 403。

#### Q5. 失败怎么办？至少一次还是至多一次？

意图至少一次（写完再 ack）。实际异常被吞仍 ack，失败变成至多一次（丢）。完整做法：失败不 ack + 重试上限 + 死信 + 表上幂等。

#### Q6. durable 队列是不是永不丢？

队列 durable，消息未必（没设 `delivery_mode=2`），也没有 confirm。进程崩、broker 没落盘、消费失败被 ack，都可能丢。对聊天记录可接受。

#### Q7. 发布 5、消费 2、MySQL 池 5，怎么配的？

发布抗多线程同时塞；INSERT 比 LLM 轻，2 个够。消费者开太多会在 MySQL 池上排队。

#### Q8. 简历「推理流水线，对话和识图进 Worker」对得上吗？

对不上字面。MQ 只有 `sql_queue`。对话非流式仍在 IO 线程；流式才进 StreamWorkerPool（不是 MQ）。识图的 **ONNX 仍同步**；后来分类结果也 publish 到同一队列落库，那是落盘不是推理异步。若真做推理流水线：taskId、202、独立队列。当时聊天页要请求-响应，不必把对话改成 MQ 异步。

#### Q9. RabbitMQ 挂了怎样？

`publish` 抛异常可能让接口 400，但内存 `push_back` 可能已经做完，出现「内存有、库没有、请求还失败」。热路径上下文仍看内存，挂的是持久化。两步没有事务。

#### Q10. 为什么不用线程池直接写库，非要 MQ？

本机线程池也能把 INSERT 挪出 IO。MQ 为了：重启后未写完还能在队列里；以后多实例共用落库通道；削峰更明确。代价是多一个中间件。课程单进程线程池其实也够。

#### Q11. 空 exchange、路由键是队列名？

默认交换机直投。现在就一个消费者组干同一件事，点对点足够。

#### Q12. Worker 池是 MQ 的吗？还有第二个流式池吗？（追问过）

不是。是 `StreamWorkerPool` 8 线程。没有第二个流式推理池。MQ 消费者是另外 2 个线程，只写库。

#### Q13. DeepSeek 网页是同步等吗？对话进 MQ 有意义吗？（追问过）

用户侧同步等这一轮；协议是长连接流式，不是 taskId 轮询。对话再进 MQ 推理队列对这个产品没意义。识图从 IO 拿开更有意义，但交互仍可一次请求等一次结果。见第 6 节。

### 9. 可能被问住怎么圆

1. 「推理也进了 MQ」— 没有。只有写库。  
2. 「识图异步」— 没有。  
3. 报吞吐百分比 — 没压测。  
4. 5 个连接是测算出来的 — 经验值。  
5. 消息绝对不丢 — 会丢。  
6. guest/localhost 写死 — 演示环境。  
7. publish 失败不回滚内存 — 承认。  
8. 消费失败仍 ack — 主动说权衡。  
9. 把 StreamWorkerPool 说成 MQ 的 worker — 两套东西。  
10. 「主线程」— 应说 IO 线程。  

---

### 10. 第四部分一句话背诵卡

- MQ 只异步写聊天记录；推理/识图别往这句上靠。  
- 5 通道轮询发布，避免单锁；2 消费者 Qos(1) + 预处理插入。  
- 简历 Worker 池 = StreamWorkerPool，不是 RabbitMQ。  
- 用户等这一轮 ≠ IO 线程去干等；DeepSeek 是长连接流式，不是交作业。  
- 失败仍 ack = 用可观测性换队列不被卡死，消息可能丢。

## 第五部分：高并发锁（读写锁 + 访问器）

对应简历：

> 针对全局锁串行化瓶颈，引入读写锁实现读路径并行。

（同一条亮点里的 MQ 轮询连接池在第四部分，本模块只讲四张内存表怎么锁。）

学完后追问过、必须一起背的：

- `shared_mutex` 和 `shared_lock` 分别是什么  
- `operator[]` 的 `[]` 是什么  
- 双重检查代码在哪，`return` 会不会放锁  
- 同一用户连传两张图会怎样（拷打题，见第 8 节）

---

### 1. 给完全没有技术背景的人讲明白

服务里有四本公共通讯录，很多窗口同时翻：

| 通讯录 | 里面是什么 | 谁在翻 |
|---|---|---|
| `chatInformation` | 用户 → 聊天窗口 → Helper | 发消息、拉历史 |
| `sessionsIdsMap` | 用户有哪些窗口 ID | 会话列表页 |
| `ImageRecognizerMap` | 用户对应的识图器 | 上传图片 |
| `onlineUsers_` | 谁已经登录 | 登录 / 登出 |

以前每本一把普通门锁（`std::mutex`）：**看书也要独占。** 发消息、拉历史、列会话，绝大多数是翻已有的页，真正新开一本很少。读也串行，IO 线程和 worker 挤在同一扇门前。

读写锁换了规矩：看书可以一堆人同时看；改通讯录必须清场只留一人。

但**只换锁类型不够。** 以前 Handler 写 `chatInformation[userId]`，方括号在 key 不存在时会偷偷插一条空的，那是写。拿着「我只是看看」的共享锁去写，是未定义行为，也让「查历史」把内存撑大。

真正的活：**禁止直接摸裸 map，全部走访问器。** 读用 `find`，写才独占，该双重检查的双重检查。加锁收口在 `ChatServer.cpp` 一处。

---

### 2. 三个词必须分清（追问过）

门和通行证不是同义词。

| 名字 | 它是什么 | 人话 |
|---|---|---|
| `std::mutex` | 一种门 | 同时只许 1 个人进。看书、改都要独占 |
| `std::shared_mutex` | **另一种门** | 看书允许多人；改必须清场 |
| `std::unique_lock` | 通行证：「我要独占」 | 别人无论看书还是改都不能进 |
| `std::shared_lock` | 通行证：「我只看书」 | 其他拿同样通行证的人可以一起看；有人要 `unique_lock` 就得等你们看完 |

```
mutable std::shared_mutex mutexForChatInformation;   // 门，一直挂在表上

{ shared_lock<shared_mutex> lock(那扇门);  /* 只查 */ }   // 出花括号自动还通行证
{ unique_lock<shared_mutex> lock(那扇门);  /* 才能插入 */ }
```

- mutex / shared_mutex = 锁本身（成员变量）  
- shared_lock / unique_lock = 这次怎么用这扇门（局部对象，出 `{}` 或 `return` 都解锁）  
- 读路径并行，靠的是很多人同时拿 `shared_lock`

`mutable`：纯读的访问器是 `const` 成员函数，但仍要加锁，所以锁标 mutable。不是逻辑上能乱改表。

---

### 3. `operator[]` 的 `[]` 是什么（追问过）

用在 `unordered_map` 上，`[]` 的正式名字叫 **`operator[]`**。

```
chatInformation[100]
```

人话：**把 100 号用户那一页翻出来。没有这一页，就当场新建一页空白的再给你。**

| 你以为自己在干嘛 | map 实际干了什么 |
|---|---|
| 查一下 100 号在不在 | 不在就 **插入** 一个空的内层 map |
| 只读 | 其实可能是 **写** |

对比：`find(100)` = 只打听，没有就说没有，什么都不插。

所以读路径一律 `find`，找不到返回 `nullptr` / 空 vector。`[]` 只允许出现在「我确定要开户」的 `unique_lock` 里。

以前拉历史 `chatInformation[userId][sessionId]`：假 sessionId 狂刷会堆出无数空 Helper。

---

### 4. 简历原句对照

| 简历怎么写 | 代码里实际是什么 | 面试怎么说 |
|---|---|---|
| 全局锁串行化瓶颈 | 原先四把 `std::mutex`，Handler 各自 `lock_guard` 再 `[]` | 属实。连拉历史都要独占 |
| 引入读写锁 | 四把换成 `std::shared_mutex` | 属实。**后来改的**，不是第一版就有 |
| 读路径并行 | `findChatHelper` / `listSessionIds` 走 `shared_lock` + `find`；已有窗口 `getOrCreate` 第一段共享锁就返回 | 属实 |
| 显著提升吞吐 | 没有压测数字 | 别报百分比 |

面试主动补：第一版四把互斥锁；改读写锁时把访问收口，过程中修了登录空窗和两把锁护同一份数据。

锁顺序约定（头文件注释）：**任何时候不同时持有下面两把及以上的表锁。** 要改两张表，拆成两段串行加锁，不嵌套。

### 5. 访问器结合代码

对应：`ChatServer.h` 82–152 行声明；`ChatServer.cpp` 82–180 行实现。

#### 5.1 纯读：`findChatHelper` / `listSessionIds`

拉历史：共享锁 → 两层 `find` → 拷出 `shared_ptr` → **解锁** → 再 `GetMessages()`。  
列会话：共享锁 → `find` → **拷贝一份 vector 再解锁**，拼 JSON 时不再持锁。

查不到就空历史 / 空列表，不建对象。多个用户同时拉可以并行。

#### 5.2 双重检查：`getOrCreateChatHelper`（代码在这）

`/chat/send` 绝大多数是往已经存在的窗口里继续说。

```
// ChatServer.cpp 约 98–126 行

// 检查 ①：很多人可以同时进来看书
{
    shared_lock lock(mutexForChatInformation);
    find userId, find sessionId;
    if (找到了) return itSession->second;   // return 也会放锁，见 5.6
}  // 没找到：走到这里时共享锁已在 } 释放

// 检查 ②：独占后再 find 一遍（这就是「双重」多出来的一眼）
unique_lock lock(mutexForChatInformation);
chatInformation[userId];           // 这里才用 []，因为真要开户
if (find sessionId 已有) return 现成的;

make_shared<AIHelper>();
emplace;
created = true;
```

**为什么 ① 和 ② 之间必须把锁放下？**  
`std::shared_mutex` 不能从共享锁直接升级成独占锁。必须出门再按独占重新排队。出门到再次进门叫空窗：两个线程同时给新 sessionId 发第一句，若不重查，会各 new 一个 Helper，后写的覆盖先写的，上下文凭空消失。

热路径：第 5 句话，检查 ① 命中，根本不进第二段。

#### 5.3 重活放锁外：`getOrCreateRecognizer`

识图器同构，多一步：构造要读 ONNX，百毫秒级。**不能占着写锁加载**，否则第一个人上传时全服识图停摆。

```
// ChatServer.cpp 约 129–147 行

{ shared_lock; find(userId); if (有) return; }   // 检查 ①，return 放锁

auto fresh = make_shared<ImageRecognizer>(路径);  // 锁已放下，慢慢加载

unique_lock;
auto result = ImageRecognizerMap.emplace(userId, fresh);  // 检查 ② 藏在 emplace
return result.first->second;
```

`emplace`：还没有 → 插入 `fresh`。已经有了 → **不覆盖**，返回别人先插的那个，自己的 `fresh` 随后析构。

第 144 行注释「先到者成功，后到者拿到已存在的那个」：**只防 map 里不要存两份**，不管推理时是否排队。见第 8 节。

Helper 很轻，可以在写锁里 `make_shared`。识图器很重，必须锁外造。用「偶尔多加载一次」换「不阻塞全服」。

磁盘上 ONNX 文件一份；内存里 **不是全服单例**，是 **每个 userId 一个** `ImageRecognizer`（每人一份 `Ort::Session`）。100 和 200 同时上传走两个对象。代价：用户多，同一份权重重复占内存。

#### 5.4 登录必须写锁：`tryMarkOnline`

防重复登录就两步：看在不在线 → 不在线就标成在线。必须在**同一把独占锁**里做完。

以前锁外判断、锁内标记：两个登录都看到不在线，双双成功（TOCTOU）。现在：

```
unique_lock;
if (已在线) return false;
onlineUsers_[userId] = true;   // 这里 [] 可以，已经决定要写
return true;
```

这张表几乎没有纯读，登录路径不吃读写锁红利。别为了「全部走 shared」把 check-and-set 拆开。

#### 5.5 两张表不许套锁

新建窗口既改 `chatInformation` 又改 `sessionsIdsMap`。若 A 先锁表1再锁表2，B 相反，会死锁。

所以拆成两段，每段干完就还锁（`ChatCreateAndSendHandler.cpp`）：

```
getOrCreateChatHelper(...)   // 用完 chat 那把锁已释放
if (created) appendSessionId(...)  // 再拿 sessions 那把锁
```

中间可能有几微秒：Helper 已经在了，侧边栏列表还没写上。用可见性延迟换没有 AB-BA。

以前的真实 bug：写 `sessionsIdsMap` 抓的是 `mutexForChatInformation`，读列表抓的是 `mutexForSessionsId`。两把门锁同一份数据，等于没锁，是数据竞争。

#### 5.6 `return` 会不会放锁？（追问过）

会。`shared_lock` / `unique_lock` 是栈上局部变量。`return` 或走出 `{ }`，析构函数里 `unlock`。

`return it->second` 的顺序：

1. 把 map 里那个 `shared_ptr` **复印一份**当返回值（引用计数 +1）  
2. 销毁 `lock` → 锁释放  
3. 调用方拿到指针复印件  

后面 `chat()` / `PredictDetailFromBuffer` **已经不拿着表锁**。锁只管「通讯录这一页在不在」，不管「模型正在算哪张图 / 窗口里正在写哪句话」。

对象不会因为放锁就拆掉：每人手里一份 `shared_ptr`，引用计数 ≥ 1，对象活着。

### 6. 锁保护什么、不保护什么

```
发消息热路径：
  getOrCreateChatHelper
    shared_lock → find 命中 → 拷出 shared_ptr → 解锁
  chat()     ← 此时已经不持表锁
    调模型、addMessage（改的是 Helper 自己的 messages）
```

**表锁保护的是窗口目录，不是对话正文，也不是 ONNX 推理。**

`AIHelper::messages` **没有**自己的互斥锁。同一窗口两条请求并发 `chat()`，理论上在 `messages` 上竞态。产品上一个窗口前端通常一次一条；两个标签 + 流式 worker 之后并发是可能的。别吹「整个对话链路无锁安全」。

Muduo 同一条 TCP 粘在同一个 IO 线程，同一浏览器标签连点，撞得少，不是语言级保证。

### 8. 拷打题：同一用户连传两张图会怎样（必须背）

#### 8.1 先把三件事情拆开

面试官一问「模型只有一份，怎么保证不同时调用」，里面其实混了三件事：

| | 对话（通义/豆包） | 识图（本地 ONNX） |
|---|---|---|
| 算力在哪 | 云厂商，他们扛并发 | **你这台机器的 CPU** |
| 内存里几份 | 每次 chat 一个轻量策略对象，真正算在云上 | **每个 userId 一个** `ImageRecognizer`，不是全服单例 |
| 同时调两次 | 两次 HTTP，一般没问题 | 两次 `Session::Run` 可能打进**同一个** session |

磁盘上 `mobilenetv2-7.onnx` 一份。用户 100 和 200 同时上传，走两个 `ImageRecognizer`、两套 `Ort::Session`，不抢「唯一那一个」。代价是权重重复占内存。

`emplace`（约 144 行）只保证：**同一个 userId 在 map 里只挂一个识图器**。第一次并发加载时两人可能各 new 一份，后到者那份析构。它不保证用的时候排队。

#### 8.2 同一用户连传两张图，时间线

识图器已经在 map 里：

```
请求 A（图1）                      请求 B（图2，同一 userId）
getOrCreateRecognizer
  shared_lock，find 命中
  复印 shared_ptr，return，放锁
开始 PredictDetailFromBuffer
  ←—— 此时表锁是空的 ——→     getOrCreateRecognizer
                                同样 find 命中，同一份指针
                                也开始 PredictDetailFromBuffer
两个人同时在跑同一份 Ort::Session
```

`AIUploadSendHandler` 第 44 行拿到指针，第 62 行 Predict。中间没有再加锁。`ImageRecognizer` 类里也 **没有 mutex**。构造时 `SetIntraOpNumThreads(1)` 只限制**单次** Run 内部用几根线程，不是「全 session 同时只许一次 Run」。

#### 8.3 会怎样（诚实说，按这个答）

- **对象会不会被拆掉？** 一般不会。两个 `shared_ptr` 引用计数 ≥ 2。  
- **会不会把对方的图分类错到自己响应里？** 每次 Predict 用的是自己栈上的图、自己的输出张量，结果绑在这次调用上，不会「A 的 HTTP 返回 B 的标签」这种交叉。  
- **会不会算乱 / 崩溃 / 变慢？** 表锁不管这件事。ONNX Runtime 文档允许同一 `Session::Run` 并发；项目没再包锁，也没压测「同一用户双图齐飞」。CPU 上两次推理抢核，延迟可能变差；极端实现/版本下并发 Run 仍有风险。  
- **面试禁止说的话：** 「读写锁保证同时只有一个请求在跑识图。」那把锁在 return 时已经放下了。

和对话对比一句话：对话并发等于多打几次云 API；识图并发等于两个人同时用你进程里的同一份本地 session，更娇贵，但当前代码和调 API 一样查完表就各跑各的。

同一窗口并发 `chat()` 改 `messages` 是同类问题，而且 `vector` 并发写是明确的数据竞争（比 ONNX 更硬）。识图至少还有「文档声称 Run 线程安全」；`messages` 没有。

#### 8.4 优化方向（防止被追问「那你打算怎么改」）

按「改动小 → 改动大」说，表明你知道缺口，不是被问住才承认。

**① 识图器内部加一把锁（最小、最该先做）**

```
class ImageRecognizer {
    mutex mtx_;
    ImagePrediction PredictDetailFromMat(...) {
        lock_guard lock(mtx_);
        // 预处理 + session->Run + softmax
    }
};
```

同一用户两张图变成排队，延迟可预期，不会并发进同一 session。不同用户仍是不同对象，互不影响。面试就说：表锁管目录，模型锁管推理，各管一段。

**② 全服共用一个 Session，推理再排队或做队列**

现在每用户加载一份权重浪费内存。改成进程级单例 `ImageRecognizer` + 一把推理锁，或前面加任务队列、固定 N 个推理 worker。内存一份，CPU 也不被「用户数 × 并发图」打爆。代价：要处理加载失败、热更新模型。

**③ 识图不要占 IO 线程（和第四部分那句「解耦」对上，且不必改成 taskId）**

`Predict` 丢进 `StreamWorkerPool` 或独立图像池。HTTP 仍等这次结果再返回（用户还是同步等），只是 EventLoop 不被 ONNX 堵住。比把识图丢进 RabbitMQ 推理队列更适合这个产品。

**④ 不要用表的 `unique_lock` 包住整个 Predict**

那会让「一个人在推理」变成「全服识图目录停摆」，比现在更糟。重活必须锁外，和 5.3 同一原则。

**⑤ 若产品允许「稍后再看结果」**

再上 `image_task_queue` + 202 + 轮询。那是长任务模型。当前分类是百毫秒级，一般不值得。被问「简历为什么写解耦到 Worker」就落到 ③：线程池卸 IO，不是 MQ 工单。

**⑥ 聊天的 `messages` 同类补丁**

每个 `AIHelper` 一把 mutex，`addMessage` / `GetMessages` / `chat` 里改向量时加上。或规定同一 session 排队（按 sessionId 一把锁）。否则「读路径并行」只保证查表，不保证同一窗口并发写历史。

**被追问时的完整短答（背这段）：**

> 保证不了同时只有一个请求在跑识图。读写锁只保护 map 里每个用户挂一个识别器，getOrCreate 返回后锁就放了。同一用户两张图会拿到同一个 shared_ptr，并发进 Predict，识别器内部没有锁。对象靠引用计数还活着，结果各绑各的调用，但 CPU 会抢、我们也没压测并发 Run。优化我会在 Predict 上加一把模型锁做排队；更进一步全服共用一份权重；并把推理从 IO 线程卸到 worker，HTTP 仍然等这一次结果。不会用表的写锁包住整个推理，那会把全服识图目录堵住。

### 9. 面试题库

#### Q1. 为什么互斥锁会成为瓶颈？读写锁怎么缓解？

四张表读多写少。`mutex` 读也互斥。`shared_mutex` 允许多个 `shared_lock`，只有改 map 结构才 `unique_lock`。热路径窗口已存在，第一段共享锁就返回。

#### Q2. 为什么不能只把 mutex 改成 shared_mutex，Handler 原样不动？（追问过，当时没看懂）

原代码 `operator[]` 会插入，读路径其实是写。共享锁期间改容器是未定义行为，「读路径并行」也加不成。必须同时改成 `find`，并把加锁收进访问器。方括号 = `[]` = 没有就开户。

#### Q3. 双重检查在防什么？代码在哪？中间为什么要先放锁？

防空窗里两个线程各 new 一个互相覆盖。聊天：`ChatServer.cpp` 105–109 行检查 ①，117–120 行检查 ②。识图：134 行 find，146 行 emplace。不能从共享锁直接升级，必须先放再抢。

#### Q4. 识图器为什么锁外构造？会不会浪费？

加载 ONNX 太重，占写锁等于全服识图停摆。并发首次可能多造一份，失败者析构。Helper 很轻，可以在写锁里造。

#### Q5. 登录为什么不用共享锁先看一眼？

那是 check-then-act，两个请求都会以为自己是第一个。必须独占锁里一次做完。

#### Q6. 会不会死锁？两张表怎么锁？

约定不嵌套。新建会话先插 Helper，再登记 ID。列表可能短暂少一条，可接受。

#### Q7. 返回 shared_ptr 之后就解锁了，安全吗？`return` 放锁吗？

表结构安全，对象生命靠 `shared_ptr`。`return` 会放锁。不安全的是 Helper 内部 `messages` 和识图 `Predict`，表锁不管。见第 6、8 节。

#### Q8. 这和 MQ 连接池、多 IO 线程是什么关系？

三层不同并发：IO 线程管连接怎么分；Worker/MQ 管慢 IO 谁来干；本模块管多线程碰到同一份内存表怎么不踩脚。

#### Q9. 有没有数据证明更快？

没有压测。定性：热路径从独占变共享。要数字就承认没测。

#### Q10. 改造时顺手修了什么 bug？（追问过，当时没看懂）

三个故事：

1. 登录：锁外判断、锁内标记，并发双登录。收进 `tryMarkOnline`。  
2. `sessionsIdsMap`：写用 chat 那把锁、读用 sessions 那把锁，数据竞争。访问器各锁各的表。  
3. 拉历史用 `[]`：伪造 sessionId 插空 Helper。改成 find，没有就空数组。

#### Q11. 同一用户连传两张图怎么办？（追问过）

用第 8 节整段。最短版：不保证互斥；map 里每用户一个识别器；Predict 无锁；优化加模型锁 + 别用表锁包推理。

#### Q12. 本地模型只有一份，对话 API 可以随便调，为什么识图不排队？

磁盘一份，内存按用户各一份 session。即使同一份 session，当前也没排队。对话并发是多打云 HTTP；识图并发是抢本机 CPU。这是缺口，优化见 8.4。

### 10. 可能被问住怎么圆

1. 「一上来就用了读写锁」— 第一版是 mutex，后来改的。  
2. 报 QPS 翻倍 — 没测。  
3. 「全程并行」— 只是查表并行；curl、写 `messages`、ONNX Run 不在这把锁里。

7. 「emplace 保证了不会同时推理」— 只保证 map 一份指针。

### 11. 第五部分一句话背诵卡

- 读多写少用读写锁；方括号是写，读必须 find。  
- 门 = shared_mutex；只看 = shared_lock；独占 = unique_lock。  
- 热路径共享锁，新建才独占且双重检查；`return` 会放锁。  
- 重活锁外做；两表不套锁；登录看和写不能拆。  
- 锁的是窗口目录，不是对话正文，也不是 ONNX。  
- 同一用户两张图：同一 shared_ptr，并发 Predict，内部无锁；优化加模型锁，不用表写锁包推理。

### 1. 给完全没有技术背景的人讲明白

对话是把字寄到阿里云。识图是 **模型文件就在你这台机器上**，CPU 自己算。

流程像安检过机：

1. 浏览器把照片编成一长串文字（base64）POST 过来  
2. 服务端解回二进制，OpenCV 认成一张图  
3. 按 MobileNetV2 的规矩把图变成「模型爱吃的数字块」：改尺寸、BGR 变 RGB、缩到 0～1、减均值除方差、通道排成 NCHW  
4. ONNX Runtime 拿这块数字跑一遍网络，吐出约 1000 个数（ImageNet 一千类的打分）  
5. 谁最大就是类别；再做 softmax，最大那个数变成 0～1 的置信度  
6. 用下标去标签表里抄类名，JSON 立刻回给前端  
7. **另写一张小纸条**丢进 `sql_queue`：用户、文件名、类名、置信度。后院消费者写入 `image_result`。原图不进库。

「轻量级」= MobileNetV2，为 CPU/手机设计的小分类网。不是检测框、不是分割、不是你们自己训的业务模型。仓库里没有训练代码，只有推理。

**计算器 vs 对话本：** 识图引擎是按用户缓存的计算器，不记上一道题；聊天 Helper 才是每个窗口的对话本。两本通讯录，别混。

### 4. 端到端三步（对着 `PredictDetailFromMat` 讲）

对应 `ImageRecognizer.cpp` 约 91–164 行。面试要能讲「为什么必须这么预处理」。

#### 4.1 预处理：让像素长得像训练时那样

OpenCV `imread` / `imdecode` 默认是 **BGR**。MobileNetV2 训练是 **RGB**，输入大约 **224×224**，数值是 `[0,1]` 再减 ImageNet 均值、除标准差：

```
mean = 0.485, 0.456, 0.406
std  = 0.229, 0.224, 0.225
```

缺一步，分类会明显跑偏：考试卷格式必须和练习册一致。

一次 `blobFromImage` 同时做：乘 `1/255`、resize、BGR→RGB（`swapRB=true`）、HWC→NCHW。  
`scalefactor` 只能是一个数，不能三通道各除不同 std，所以后面手动按平面减均值除方差。NCHW 三个通道平面首尾相接。

动态维度（shape 里是 -1）时取不到高宽，退回 224。

#### 4.2 推理：借用内存，不要多余拷贝

```
CreateTensor(..., blobData, ...)   // 借用 blob 的指针，不是拷贝
session->Run(...)
```

`blob` 必须活到 Run 结束。它是这个函数里的局部 `cv::Mat`，Run 是同步的，return 更在后面，生命周期没问题。若改成异步推理、函数先 return，这块内存就悬了——现在没有这个问题。

输入形状 `{1, 3, H, W}`：batch=1，一张图。

#### 4.3 后处理：argmax + 数值稳定的 softmax

输出是 **logits**（没归一化的打分），不能直接当概率。

1. 类别数 = 输出张量元素个数，**不用** `labels.size()`  
2. `max_element` 得到下标（argmax）  
3. softmax：先减最大值再 `exp`，避免 `exp(很大的数)` 变成 inf。最大项减完自己是 0，`exp(0)=1`，置信度 = `1 / sumExp`  
4. 下标落在标签表里就抄类名，否则 `"Unknown"`

只回 **Top-1**。没有 Top-5，没有低于阈值返回「不确定」。

|---|---|---|

### 6. 分类结果异步落库（后来补上的，按现码背）

讨论时的结论先钉死，再讲实现：

> 落盘异步 ≠ 推理异步。旧简历「识图任务解耦到 Worker 池异步执行」说的是谁去跑 ONNX。把结果 INSERT 进 MySQL，只是算完之后记一笔账。

现在代码做的是后者，面试主动拆开。

#### 6.1 存什么、不存什么

表 `image_result`（`init_v3.sql`；启动时 `ensureImageResultTable` 也会 `CREATE IF NOT EXISTS`）：

- `user_id` / `username` / `filename`  
- `class_name` / `class_id` / `confidence`  
- `model`（现在写死 `mobilenetv2`）/ `ts`  

**不存原图、不存 base64**，避免大字段进队列和表。

不要硬塞进 `chat_message`：那张表是对话（session_id、is_user、content、token），没有置信度列。

#### 6.2 怎么走

Handler 在 Predict **成功之后**：

```
try { server_->pushImageResult(userId, username, filename, prediction); }
catch { 打日志，仍然 200 把分类结果返回 }
```

`pushImageResult` 组 JSON：`type=image_result`，然后 `MQManager::instance().publish("sql_queue", ...)`。和聊天 `pushMessageToMysql` 同一条队列、同一套 5 通道轮询发布。

`main.cpp` 的 `executeMysql` 看 `type`：

- `image_result` → 预处理 `INSERT INTO image_result (...) VALUES (?,?,...)`  
- 默认 / `chat_message` → 原来的 `chat_message` INSERT  
- 解析不成 JSON → 当旧版裸 SQL（兼容）

SQL 写死在消费端，用户字段走占位符，没有拼 SQL。

publish 失败（RabbitMQ 挂了）catch 住：用户已经看到分类，落库失败只影响以后查历史。这才是「写库从热路径拿开」。

#### 6.3 面试可以怎么说（改完代码之后）

> 识别本身仍在请求线程里跑完，用户等的是这一次结果。算完把分类结果丢进 sql_queue 异步落盘，和对话记录同一套削峰，不在 IO 线程里 INSERT。这不是把 ONNX 推理改成后台任务。

被追问「那简历那句异步执行识别任务呢」：

> 那句按字面还是没做。队列里现在有两种写：chat_message 和 image_result。计算还在前台。若要把推理从 IO 拿开，应丢进 Worker 池，HTTP 仍然等这次 Predict 结束；不必先上 taskId。

#### 6.4 和对话落库对照

| | 对话 | 识图 |
|---|---|---|
| 计算 | 云 API；流式进 StreamWorkerPool | 本地 ONNX，当前线程 |
| 热数据 | Helper 的 `messages` | 无（引擎无状态） |
| 落库 | `addMessage` → `type=chat_message` | Predict 后 → `type=image_result` |
| 队列 | 同一条 `sql_queue` | 同一条 |
| 表 | `chat_message` | `image_result` |
| 重启恢复 | `readDataFromMySQL` 灌回 Helper | **目前没有**把 `image_result` 灌回内存（也不需要，引擎无历史） |

### 9. 面试题库

#### Q1. 端到端推理具体几步？

解码（OpenCV）→ 预处理成 NCHW 浮点（缩放、RGB、ImageNet 标准化）→ ONNX `Run` → argmax + softmax → 查标签表。OpenCV 管图，ONNX 管网，Handler 管 HTTP 和异步落库。

---

#### Q2. 为什么预处理必须减均值除方差？BGR 和 RGB 搞反会怎样？

训练时像素就经过这套变换，推理必须对齐，否则等于用另一套数字进网，准确率会垮。BGR 当 RGB 送进去，通道全反，颜色相关的类会乱分。`swapRB=true` 就是为这个。

---

#### Q3. logits 和概率有什么区别？为什么要 softmax？为什么先减 max？

logits 是原始打分，可正可负，加起来不是 1。softmax 变成和为 1 的概率。直接 `exp` 在打分很大时会溢出；先减最大值，最大项变 0，指数上界 1，结果和减之前等价。以前写死 0.95 等于撒谎；现在前端看到的是 Top-1 真实概率。

---

#### Q4. 为什么类别数看张量长度，不看标签行数？

标签文件多一行时，按 `labels.size()` 扫会读输出缓冲区后面的内存。长度以模型为准，下标超出标签就 `Unknown`。

---

#### Q5. 这是检测还是分类？是你们自己训的吗？

分类：整图一个类名。检测要框和多目标，这套输出是约 1000 维向量。权重是公开 MobileNetV2-ImageNet，没有用业务数据重训。换自己的 onnx，均值方差、输入尺寸、标签表都要跟着换。

---

#### Q6. 为什么 IntraOp 设成 1？为什么不用 GPU？

一次请求不要吃光所有核，否则同 IO 线程上别的连接一起卡。GPU 要 CUDA 版 ORT、驱动、拷贝。CPU + 轻量级模型够分类演示。量上来再评估 GPU 或独立推理进程。

---

#### Q7. 输入张量为什么借用 blob 内存？会悬空吗？

少一次拷贝。`blob` 是局部 Mat，`Run` 同步，Run 返回前 Mat 还在。若改成异步推理、函数先 return，就必须拷贝或延长生命。现在没有这个问题。

---

#### Q8. 识图为什么还在 IO 线程？和简历「Worker 池」的关系？

现状：Predict 同步堵在当前线程。正确卸法是丢进计算池，**HTTP 仍等这一次结果**，不必做成 taskId。双图并发、内部无锁见第五部分第 8 节。对话流式已经卸 IO，识图还没卸。队列只负责写 `image_result`。

---

#### Q9. 每用户加载一份模型，内存不浪费吗？

浪费。识图器推理时没有用户私有权重，本可全服一份 Session + 推理锁或 worker 队列。现在按 userId 缓存，是和 Helper「每用户一个对象」抄过来的；Helper 有历史所以必须分开，识图器没有。

---

#### Q10. 置信度 0.4 会拒识吗？只返回 Top-1 够不够？

不会拒。没有阈值。0.4 也会把类名返回去。可以加 uncertain 或 Top-5，现在没有。

---

#### Q11. `getOrCreateRecognizer` 和聊天是不是同一张 map？（追问过）

不是。聊天是 `chatInformation` 两层 map 到 AIHelper；识图是 `ImageRecognizerMap` 一层到 ImageRecognizer。AIHelper 没有图片字段。见第 5 节。

---

#### Q12. 结果存 MySQL 了，是不是就能说识图异步进了 Worker？（追问过，改完代码后）

不能。存库是异步落盘，Predict 仍同步。`type=image_result` 和 `chat_message` 共用 `sql_queue`。面试把「谁算」和「谁写库」拆开。见第 6.3 节。

---

#### Q13. 为什么不把图也存进 MySQL？

原图/base64 很大，塞进 RabbitMQ 和 InnoDB 会拖垮削峰。产品要的是分类历史（谁、什么文件、什么类、多有把握），不是图床。图若要留，应对象存储，表里只存 URL。

---

#### Q14. publish 失败为什么还 200？

分类已经算完，用户要的是这次结果。落库失败只打日志，避免 MQ 抖动把成功的识别变成 400。和「写库从热路径解耦」一致。聊天 `addMessage` 若 publish 抛错仍可能让 chat 失败，识图这里单独兜住了。

### 10. 可能被问住怎么圆

1. **「我们训了图像模型」** — 没有。预训练分类。  
2. **「目标检测 / OCR / 人脸」** — 就是 ImageNet 分类。  
3. **「识图任务进了 MQ 异步执行」** — 执行（ONNX）没有；落库有。  
4. **置信度一直很准** — 曾经假 0.95，现在才是 softmax。  
5. **读写锁保证推理互斥** — 不保证，见第五部分第 8 节。  
6. **端到端含训练** — 只含推理。  
7. **OpenCV 也能跑 DNN，为什么还要 ORT** — OpenCV DNN 也能读 onnx；选 ORT 是更常见的推理引擎、和训练导出链路一致。  
8. **重启后能看到识图历史** — 表里有；目前没有做「识图历史」HTTP 接口从库里拉给前端。被问到承认：只落库，没做查询页。  
9. **AIHelper 里带着图** — 没有。两张 map。

### 11. 第六部分一句话背诵卡

- 本地 MobileNetV2 分类；OpenCV 把图变成训练时那种张量，ORT 跑网，softmax 出真实置信度。  
- 同步 Predict，占 IO；结果 publish 到 sql_queue 落 image_result，不存原图。  
- 落盘异步 ≠ 推理异步。  
- 识图 map 按 userId 缓存引擎，不是 chatInformation，Helper 里没有图。  
- 双图并发不在表锁里，优化加模型锁；别用表写锁包住 Predict。  
- 预训练分类，不是自研检测。
