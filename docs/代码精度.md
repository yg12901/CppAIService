# CppAIService 代码说明（对照当前仓库）

> 以仓库源码为准。关键路径把函数怎么写、为什么这么写讲清楚。入口页那种「读个 HTML 返回」不逐个贴。设计模式附录不写。
>
> 面试话术看 `docs/面试准备文档.md`。

---

## 一、它现在是什么

单进程 C++ HTTP 服务，可执行文件 `http_server`。Muduo 管 TCP，HTTP 自己拆。业务在 `AIApps/ChatServer`。

两套 session 不要混：

- Cookie Session：登录态（`isLoggedIn` / `userId` / `canChat`）
- 聊天 `sessionId`：一个窗口，对应一个 `AIHelper`，里面有这份对话的 `messages`

| 能力 | 代码落点 |
|---|---|
| 多模型 | `modelType` `"1"`–`"4"`，`chat()` 里 `StrategyFactory::create` |
| RAG | `"3"` `AliyunRAGStrategy`，云端应用一次返回。灌库走 `/kb/upload`，共享库 |
| MCP | `"4"` Helper 里两段式 + `AIConfig` 四层解析 |
| 流式 | `StreamWorkerPool` + `SseParser`；RAG 关流式 |
| 识图 | 每用户一个 ONNX Session，同步 `Predict`，JSON 进 `sql_queue` |
| 落库 | 内存先写，MQ 丢 JSON，消费端预处理 INSERT |

## 三、CMake：为什么要踢掉一份 main.cpp

```cmake
file(GLOB_RECURSE GOMOKU_SERVER_SRC
    "${PROJECT_SOURCE_DIR}/AIApps/ChatServer/src/*.cpp"
)
list(REMOVE_ITEM GOMOKU_SERVER_SRC "${PROJECT_SOURCE_DIR}/AIApps/ChatServer/src/main.cpp")

set(MAIN_SRC "${PROJECT_SOURCE_DIR}/AIApps/ChatServer/src/main.cpp")

add_executable(http_server
    ${MAIN_SRC}
    ${HTTP_SERVER_SRC}
    ${GOMOKU_SERVER_SRC}
)
```

`GLOB_RECURSE` 已经把 `src/main.cpp` 收进去了。再 `set(MAIN_SRC ...)` 不加 `REMOVE_ITEM`，`main` 会定义两次，链接失败。变量名 `GOMOKU_SERVER_SRC` 是五子棋项目留下来的，和功能无关。

C++17。链接 muduo、mysqlcppconn、curl、OpenCV、onnxruntime、SimpleAmqpClient。

## 四、入口 main.cpp：消费端才写 SQL

队列里不再是拼好的 INSERT。`executeMysql` 解析 JSON，语句写死，参数走 `?`。

```cpp
void executeMysql(const std::string msg) {
    http::MysqlUtil mysqlUtil_;

    json payload = json::parse(msg, nullptr, false);   // 失败不抛，返回 discarded
    if (payload.is_discarded() || !payload.is_object()) {
        // 升级期间队列里可能还堆着上一版裸 SQL
        LOG_WARN << "legacy raw-sql message in queue, executing as-is";
        mysqlUtil_.executeUpdate(msg);
        return;
    }

    const std::string type = payload.value("type", std::string("chat_message"));

    try {
        if (type == "image_result") {
            static const std::string kInsertImageResult =
                "INSERT INTO image_result "
                "(user_id, username, filename, class_name, class_id, confidence, model, ts) "
                "VALUES (?, ?, ?, ?, ?, ?, ?, ?)";
            // ... 从 payload 取值，executeUpdate(kInsertImageResult, ...)
            return;
        }

        static const std::string kInsertChatMessage =
            "INSERT INTO chat_message "
            "(id, username, session_id, is_user, content, ts, model, prompt_tokens, completion_tokens) "
            "VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?)";
        // session_id 空则写成 "0"，避免绑空串
        // ...
    }
    catch (const std::exception& e) {
        LOG_ERROR << "insert " << type << " failed: " << e.what();
    }
}
```

`json::parse(msg, nullptr, false)` 第三个参数关异常：消费线程里抛出会让这条消息 Ack 与否变得难控。旧消息走 `executeUpdate(msg)` 是兼容，积压清完可以删。

`main` 顺序：

```cpp
ChatServer server(port, serverName);   // 里面已经起了 StreamWorkerPool(8) 和 SSE 心跳
server.setThreadNum(4);                // Muduo：1 主 loop + 4 IO
std::this_thread::sleep_for(std::chrono::seconds(2));
server.initChatMessage();              // 从 chat_message 灌回内存
RabbitMQThreadPool pool("localhost", "sql_queue", 2, executeMysql);
pool.start();
server.start();                        // 阻塞进事件循环
```

先灌库再开 HTTP，避免请求打到空的 `chatInformation`。MQ 消费和 HTTP 并行：内存里的 `messages` 不依赖 INSERT 成功。

## 五、HTTP 半包：状态机挂在连接上

连接建立时，把 `HttpContext` 塞进这条连接的 context。之后每次 `onMessage` 都拿同一个对象继续解。

```cpp
void HttpServer::onConnection(const muduo::net::TcpConnectionPtr& conn)
{
    if (conn->connected())
    {
        conn->setContext(HttpContext());   // state_ 从 kExpectRequestLine 开始
    }
}
```

```cpp
void HttpServer::onMessage(..., Buffer *buf, Timestamp receiveTime)
{
    HttpContext *context = boost::any_cast<HttpContext>(conn->getMutableContext());
    if (!context->parseRequest(buf, receiveTime))
    {
        conn->send("HTTP/1.1 400 Bad Request\r\n\r\n");
        conn->shutdown();
        return;
    }
    if (context->gotAll())
    {
        onRequest(conn, context->request());
        context->reset();   // 同一条 Keep-Alive 连接上下一个请求从头解
    }
    // 没 gotAll：半包，buf 里剩下的字节留着，等下一次 onMessage
}
```

`parseRequest` 三个状态。**关键是 body**：`readableBytes() < Content-Length` 时返回 `true`（语法没错），`state_` 停在 `kExpectBody`，**不**当失败、不让客户端重发。

```cpp
else if (state_ == kExpectBody)
{
    if (buf->readableBytes() < request_.contentLength())
    {
        hasMore = false;
        return true;   // 数据不完整，等更多 TCP 段
    }
    std::string body(buf->peek(), buf->peek() + request_.contentLength());
    request_.setBody(body);
    buf->retrieve(request_.contentLength());
    state_ = kGotAll;
    hasMore = false;
}
```

头解析碰到空行（`buf->peek() == crlf`）才根据方法决定要不要进 `kExpectBody`。POST 没有 `Content-Length` 才把 `ok` 置 false。

Muduo `setThreadNum(4)`：1 个主 loop 只 accept，连接 sticky 到某一个 IO 线程。同一连接的两次半包一定在同一线程、同一个 `HttpContext` 上，所以状态机不用加锁。

齐包之后 `onRequest`。Handler 若 `setStreaming(true)`，框架**不再** `appendToBuffer` 把整包响应写出去，避免和 worker 抢着写同一条连接：

```cpp
response.setConnection(conn);   // Handler 用来构造 SseChannel
httpCallback_(req, &response);

if (response.isStreaming())
{
    if (response.closeConnection())
        conn->shutdown();
    return;   // 跳过统一序列化
}
```

ChatSendHandler 里流式是 `setCloseConnection(false)`，关连接的是 worker 发完 `[DONE]` 之后的 `channel->close()` → `conn->shutdown()`。

## 六、ChatServer：四张表只许走访问器

### 6.1 成员

```cpp
// 锁顺序：任何时候不同时持下面两把及以上的锁。
std::unordered_map<int, bool> onlineUsers_;
mutable std::shared_mutex mutexForOnlineUsers_;

std::unordered_map<int, std::unordered_map<std::string, std::shared_ptr<AIHelper>>> chatInformation;
mutable std::shared_mutex mutexForChatInformation;

std::unordered_map<int, std::shared_ptr<ImageRecognizer>> ImageRecognizerMap;
mutable std::shared_mutex mutexForImageRecognizerMap;

std::unordered_map<int, std::vector<std::string>> sessionsIdsMap;
mutable std::shared_mutex mutexForSessionsId;
```

`mutable` 是因为纯读访问器是 `const` 成员，但仍要上锁。`shared_mutex`：读多写少，拉历史/继续聊可以并行。

Handler 全部 `friend`，但约定不准直接碰裸 map。改造前每个 Handler 自己 `lock_guard`，漏锁、用错锁、`operator[]` 当只读，都出过。

### 6.2 启动时还做两件和聊天无关的事

```cpp
void ChatServer::initialize() {
    http::MysqlUtil::init("tcp://127.0.0.1:3306", "root", "123456", "ChatHttpServer", 5);
    ensureImageResultTable();
    initializeSession();
    initializeMiddleware();
    initializeRouter();

    StreamWorkerPool::instance().start(8);

    httpServer_.getLoop()->runEvery(5.0, []() {
        SseKeepalive::instance().onTimer();
    });
}
```

8 个 worker 专门跑「阻塞 curl + 往浏览器推 delta」。心跳挂在**主 loop**上，每 5 秒扫活跃 SSE。

`ensureImageResultTable` 是 `CREATE TABLE IF NOT EXISTS`，忘跑 SQL 脚本时消费端不会一直 INSERT 失败。

### 6.3 find：只查不建

```cpp
std::shared_ptr<AIHelper> ChatServer::findChatHelper(int userId,
    const std::string& sessionId) const
{
    std::shared_lock<std::shared_mutex> lock(mutexForChatInformation);
    auto itUser = chatInformation.find(userId);
    if (itUser == chatInformation.end()) return nullptr;
    auto itSession = itUser->second.find(sessionId);
    if (itSession == itUser->second.end()) return nullptr;
    return itSession->second;
}
```

必须用 `find`。`operator[]` 在 key 不存在时插入默认值，是写；`shared_lock` 下写是未定义行为。旧 `ChatHistoryHandler` 查伪造 `sessionId` 还会在 map 里塞空 Helper。

锁是局部对象，`return` 时析构解锁。返回的是 `shared_ptr` 拷贝，调用方用 Helper 时已经不持表锁。

### 6.4 getOrCreate：双重检查

```cpp
std::shared_ptr<AIHelper> ChatServer::getOrCreateChatHelper(int userId,
    const std::string& sessionId, bool* created)
{
    if (created) *created = false;

    {
        std::shared_lock<std::shared_mutex> lock(mutexForChatInformation);
        auto itUser = chatInformation.find(userId);
        if (itUser != chatInformation.end()) {
            auto itSession = itUser->second.find(sessionId);
            if (itSession != itUser->second.end()) return itSession->second;
        }
    }   // 释放共享锁

    std::unique_lock<std::shared_mutex> lock(mutexForChatInformation);
    auto& userSessions = chatInformation[userId];
    auto itSession = userSessions.find(sessionId);
    if (itSession != userSessions.end()) return itSession->second;  // 第二次检查

    auto helper = std::make_shared<AIHelper>();
    userSessions.emplace(sessionId, helper);
    if (created) *created = true;
    return helper;
}
```

`/chat/send` 绝大多数是往已有窗口发，第一段 `shared_lock` 就返回。只有窗口第一条消息才抢写锁。

释放共享锁到拿到独占锁之间有空窗。两个线程同时为同一个新 `sessionId` 进来，若写锁里不再查，会各 `make_shared` 一个 Helper，后 `emplace`/赋值覆盖先写入的，上下文丢。第二次 `find` 就是堵这个空窗。

`AIHelper` 构造很轻（只 `create("1")` 一个策略），所以可以在写锁里 `make_shared`。识图不行，见下。

### 6.5 识图：锁外构造

```cpp
std::shared_ptr<ImageRecognizer> ChatServer::getOrCreateRecognizer(int userId)
{
    {
        std::shared_lock<std::shared_mutex> lock(mutexForImageRecognizerMap);
        auto it = ImageRecognizerMap.find(userId);
        if (it != ImageRecognizerMap.end()) return it->second;
    }

    auto fresh = std::make_shared<ImageRecognizer>(imageModelPath());  // 读 ONNX，百毫秒

    std::unique_lock<std::shared_mutex> lock(mutexForImageRecognizerMap);
    auto result = ImageRecognizerMap.emplace(userId, fresh);
    return result.first->second;   // 后到者拿到先到者的，fresh 析构
}
```

`imageModelPath()` 读环境变量 `IMAGE_MODEL_PATH`，否则 `/root/models/mobilenetv2/mobilenetv2-7.onnx`。

两个线程同时首次上传：可能白造一份。`emplace` 只有先到者插入成功。用「偶尔多造一份」换「不把全服识图堵在写锁上」。

`Predict*` 没有识别器内部锁。访问器交出 `shared_ptr` 就放表锁。同一用户两张图并发会在同一个 `Ort::Session` 上 `Run`。

### 6.6 登录必须原子

```cpp
bool ChatServer::tryMarkOnline(int userId)
{
    std::unique_lock<std::shared_mutex> lock(mutexForOnlineUsers_);
    auto it = onlineUsers_.find(userId);
    if (it != onlineUsers_.end() && it->second) return false;
    onlineUsers_[userId] = true;
    return true;
}
```

旧实现锁外判断、锁内标记，并发登录能双双成功。现在判断和写入在同一把写锁里。

### 6.7 会话 ID 列表：两段锁，不嵌套

```cpp
void ChatServer::appendSessionId(int userId, const std::string& sessionId)
{
    std::unique_lock<std::shared_mutex> lock(mutexForSessionsId);
    sessionsIdsMap[userId].push_back(sessionId);
}

std::vector<std::string> ChatServer::listSessionIds(int userId) const
{
    std::shared_lock<std::shared_mutex> lock(mutexForSessionsId);
    auto it = sessionsIdsMap.find(userId);
    if (it == sessionsIdsMap.end()) return {};
    return it->second;   // 拷贝出去再拼 JSON
}
```

`ChatCreateAndSendHandler` 以前在 `mutexForChatInformation` 保护下写 `sessionsIdsMap`，而 `/chat/sessions` 用的是 `mutexForSessionsId`，两把锁护同一份数据，是数据竞争。现在：

```cpp
bool created = false;
auto AIHelperPtr = server_->getOrCreateChatHelper(userId, sessionId, &created);
if (created) {
    server_->appendSessionId(userId, sessionId);   // 前一把锁已释放
}
```

### 6.8 灌库也走访问器

```cpp
helper->restoreMessage(content, ts, is_user != 0);
```

`restoreMessage` 只推进内存，不走 MQ，避免重启把同一批话再 INSERT 一遍。第三个参数把库里的 `is_user` 转成 role，旧签名丢掉了这个字段，恢复后只能靠奇偶猜。

## 七、策略：role 写在消息上

### 7.1 ChatMessage

```cpp
struct ChatMessage {
    std::string role;     // "user" / "assistant" / "system"
    std::string content;
    long long   timestamp{0};
};

inline const char* roleFromIsUser(bool is_user) {
    return is_user ? "user" : "assistant";
}
```

发给厂商的 JSON 里一直有 `role`。以前内存只存 `(content, ts)`，`buildRequest` 里 `i % 2 == 0` 当 user。MCP 临时句 push 之后若没 pop 干净，后面整盘人/AI 错位。

### 7.2 组请求：读字段，不猜下标

```cpp
json messagesToArray(const std::vector<ChatMessage>& messages) {
    json msgArray = json::array();
    for (const auto& m : messages) {
        json msg;
        msg["role"] = m.role;
        msg["content"] = m.content;
        msgArray.push_back(std::move(msg));
    }
    return msgArray;
}

json AliyunStrategy::buildRequest(const std::vector<ChatMessage>& messages) const {
    json payload;
    payload["model"] = getModel();          // "qwen-plus"
    payload["messages"] = messagesToArray(messages);
    return payload;
}

json AliyunRAGStrategy::buildRequest(const std::vector<ChatMessage>& messages) const {
    json payload;
    payload["input"]["messages"] = messagesToArray(messages);
    payload["parameters"] = json::object();
    return payload;
}
```

百炼/豆包/MCP 都是 OpenAI 兼容。RAG 多套一层 `input`，回执走 `output.text`，所以不能和另外三家共用一个策略只改 URL。

```cpp
std::string AliyunRAGStrategy::getApiUrl() const {
    const char* key = std::getenv("Knowledge_Base_ID");
    if (!key) throw std::runtime_error("Knowledge_Base_ID not found!");
    return "https://dashscope.aliyuncs.com/api/v1/apps/" + std::string(key) + "/completion";
}
```

流式开关：

```cpp
virtual bool isStreamSupported() const { return false; }   // 基类默认
// Aliyun / DouBao / Mcp override 为 true
// RAG 不 override → Handler 自动走整包 JSON
```

豆包模型名写死：

```cpp
std::string DouBaoStrategy::getModel() const {
    return "doubao-seed-1-6-thinking-250715";
}
```

这个 ID 若 Key 未开通，火山 404 JSON。SseParser 只抽 `delta.content`，界面就是空泡。要去火山方舟换接入点 ID，不是换窗口把库写坏了。

### 7.3 工厂：main 前自己报到

```cpp
template<typename T>
struct StrategyRegister {
    StrategyRegister(const std::string& name) {
        StrategyFactory::instance().registerStrategy(name, [] {
            return std::make_shared<T>();
        });
    }
};

static StrategyRegister<AliyunStrategy>    regAliyun("1");
static StrategyRegister<DouBaoStrategy>    regDoubao("2");
static StrategyRegister<AliyunRAGStrategy> regAliyunRag("3");
static StrategyRegister<AliyunMcpStrategy> regAliyunMcp("4");
```

全局 `static` 对象在 `main` 之前构造。工厂用 Meyers 单例（`instance()` 里的 `static StrategyFactory`），第一次 `registerStrategy` 才创建表，没有「工厂还是空的」那种静态初始化顺序坑。

```cpp
std::shared_ptr<AIStrategy> StrategyFactory::create(const std::string& name) {
    auto it = creators.find(name);
    if (it == creators.end())
        throw std::runtime_error("Unknown strategy: " + name);
    return it->second();   // 每次 new，不缓存
}
```

策略对象很轻（主要是一个 key 字符串）。每次 `create` 能读到新的环境变量，单例缓存还要考虑 Key 轮换。

`AliyunMcpStrategy` 构造里 `isMCPModel = true`。Helper 靠这个字段决定走不走两段式，不是看编号字符串。

## 八、AIHelper：一轮对话的全部写法

### 8.1 正式历史 vs 临时槽

```cpp
void AIHelper::addMessage(int userId, const std::string& userName, bool is_user,
                          const std::string& userInput, std::string sessionId) {
    auto ms = /* 毫秒时间戳 */;
    messages.push_back({ roleFromIsUser(is_user), userInput, ms });
    pushMessageToMysql(userId, userName, is_user, userInput, ms, sessionId);
}

void AIHelper::restoreMessage(const std::string& userInput, long long ms, bool is_user) {
    messages.push_back({ roleFromIsUser(is_user), userInput, ms });
}
```

`addMessage` = 内存立刻有 + MQ 异步入库。MCP 内部提示词是：

```cpp
messages.push_back({ "user", tempUserQuestion, 0 });
// executeCurl ...
messages.pop_back();   // 不走 addMessage，所以不入库
```

| | 临时 `push_back` + `pop_back` | `addMessage` |
|---|---|---|
| 进 `messages` | 只在这一次 curl 期间 | 长期留着 |
| 进 MySQL | 否 | 是 |
| 例子 | 「只准输出 JSON」提示词、第二段工具结果稿 | 「广州天气」+ 最终人话 |

### 8.2 chat() 开头：每轮现场选策略

```cpp
std::string AIHelper::chat(..., std::string modelType, bool stream) {
    m_curModel = modelType;
    m_lastPromptTokens = 0;
    m_lastCompletionTokens = 0;
    m_abortRequested.store(false);
    m_chatStart = std::chrono::steady_clock::now();

    setStrategy(StrategyFactory::instance().create(modelType));

    const bool useStream = stream && strategy->isStreamSupported() && m_streamCallback;

    struct CallbackGuard {
        std::function<void(const std::string&)>& slot;
        ~CallbackGuard() { slot = nullptr; }
    } cbGuard{m_streamCallback};
```

`CallbackGuard` 防止回调跨请求悬挂。Handler 每次 `setStreamCallback` 再调 `chat`。

`useStream` 三个条件缺一不可。RAG 的 `isStreamSupported()` 为 false，即使前端传了 `stream:true` 也走整包。

### 8.3 非 MCP：先落用户句，再带整段历史

```cpp

    json payload = strategy->buildRequest(this->messages);

    std::string answer;
    if (useStream) {

        json streamPayload = payload;
        streamPayload["stream"] = true;
        try {
            json response = executeCurl(streamPayload);
            answer = strategy->parseResponse(response);
        } catch (const std::exception& e) {
            if (m_abortRequested) {
                answer = m_streamedAnswer;
            } else if (m_streamDeltaCount == 0) {
                answer = strategy->parseResponse(executeCurl(payload));  // 降级非流式
            } else {
                answer = m_streamedAnswer;   // 已有增量，不当失败重打
            }
        }
    } else {
        answer = strategy->parseResponse(executeCurl(payload));
    }

    addMessage(userId, userName, false, answer, sessionId);
    return answer.empty() ? "[Error] 无法解析响应" : answer;
}
```

注意顺序：用户原话在 curl **之前**就 `addMessage` 了。`buildRequest(this->messages)` 带的是**整段正式历史**（含刚写下的这句，含以前别的模型说过的），不是「只寄最后一句」。

流式 Handler **不用**这个返回值往浏览器推，只靠回调。解析失败得到空串时，仍会 `addMessage` 一条空 assistant，前端可能只看到 `[DONE]`。

### 8.5 executeCurl / WriteCallback

```cpp
json AIHelper::executeCurl(const json& payload) {
    CURL* curl = curl_easy_init();
    CurlCtx ctx;
    ctx.self = this;
    ctx.wantStream = payload.value("stream", false) && m_streamCallback != nullptr;

    // Authorization: Bearer + Content-Type: application/json
    curl_easy_setopt(curl, CURLOPT_URL, strategy->getApiUrl().c_str());
    curl_easy_setopt(curl, CURLOPT_POSTFIELDS, payloadStr.c_str());
    curl_easy_setopt(curl, CURLOPT_WRITEFUNCTION, WriteCallback);
    curl_easy_setopt(curl, CURLOPT_WRITEDATA, &ctx);
    // 没有 CURLOPT_TIMEOUT

    CURLcode res = curl_easy_perform(curl);
    if (res != CURLE_OK)
        throw std::runtime_error("curl_easy_perform() failed: " + std::string(curl_easy_strerror(res)));

    if (ctx.wantStream && !m_sse.plainJson && (m_streamDeltaCount > 0 || m_sse.done)) {
        // flush pending 尾巴，拼 fake choices[0].message.content
        json fake;
        fake["choices"] = json::array({ json{{"message", json{{"content", m_streamedAnswer}}}} });
        return fake;   // parseResponse 无感
    }

    json response = json::parse(ctx.buffer);   // 非流式或对方没按 SSE 回
    // 累加 usage
    return response;
}
```

没有超时：思考模型可以挂很久。没有 `CURLOPT_FAILONERROR`：HTTP 404 仍当成功，body 当 JSON 解析；豆包模型不存在时 `parseResponse` 找不到 `choices`，得到空串。

```cpp

           conn_->outputBuffer()->readableBytes() > kBackpressureBytes) {  // 1MB
```

背压：浏览器收得慢 → Muduo 输出缓冲涨 → worker `sleep` → curl 的 WriteCallback 被挡住 → TCP 窗口反压上游 LLM。心跳 `sendPing` 不走背压，避免定时器线程被 sleep 卡住。

`conn->send` 由 Muduo 转到连接所属 IO 线程，worker 调它是线程安全的。

### 10.3 StreamWorkerPool

```cpp
void StreamWorkerPool::submit(Task task) {
    {
        std::lock_guard<std::mutex> lk(mtx_);
        tasks_.push(std::move(task));
    }
    cv_.notify_one();
}

void StreamWorkerPool::workerLoop() {
    for (;;) {
        Task task;
        {
            std::unique_lock<std::mutex> lk(mtx_);
            cv_.wait(lk, [this] { return stopping_ || !tasks_.empty(); });
            if (stopping_ && tasks_.empty()) return;
            task = std::move(tasks_.front());
            tasks_.pop();
        }
        if (task) task();   // 异常必须任务自己 catch，否则打死 worker
    }
}
```

ChatServer 启动 `start(8)`。任务里是完整的 `chat(..., true)`，会阻塞在 curl 上，所以不能放 IO 线程：4 条流就会占满 4 个 IO，同 loop 上别的连接全饿死。

### 10.4 心跳

```cpp
void SseKeepalive::onTimer() {
    std::lock_guard<std::mutex> lk(mtx_);
    for (auto it = flows_.begin(); it != flows_.end();) {
        auto ch = it->second.lock();
        if (!ch || !ch->alive()) { it = flows_.erase(it); continue; }
        if (ch->idleMs() > 10000)
            ch->sendPing();   // ": ping\n\n"，SSE 注释，前端零改动
        ++it;
    }
}
```

表里存 `weak_ptr`：worker 崩了没注销，下一轮扫描也能清。注册/注销来自 Handler 与 worker，定时器在主 loop，所以要加锁。

为什么不用 curl 进度回调发心跳：进度回调只在传输期间触发，盖不住 MCP「第一段结束 → 工具 5 秒 → 第二段开始」那段完全没字节的空窗。

### 12.2 四层候选，再逐个校验

```cpp
AIToolCall AIConfig::parseAIResponse(const std::string& response) const {
    std::vector<Candidate> candidates;
    // L0 整段 JSON
    // L1 剥 ```json ... ```
    // L2 括号配对从闲聊里抠 {...}（字符串和转义里的 } 不算）
    // L3 仅当前三层全空：正则抽 tool / args；中文冒号写成 (?::|：)
    //    不能写字符类 [:：]——std::regex 按字节匹配，U+FF1A 三字节会拆开

    for (auto& c : candidates) {
        AIToolCall cur = validateToolCall(c.obj);
        if (cur.isToolCall) return cur;
        // 留下第一条「长得像工具但没过校验」的 rejectReason
    }
    return result;   // isToolCall=false
}
```

L3 必须最后且带「前三层全空」前提：用户正常聊天里写 `tool: '锤子'` 也会被宽松正则命中。

### 12.3 validateToolCall

- `tool` 必须是字符串且在 `config.json` 白名单
- `args` 可以是对象，也可以是再套一层的 JSON 字符串

- 模型多塞的字段（幻觉 `unit`）进不了 `cleaned`，不会传到 `invoke`

过不了：`isToolCall=false` + `rejectReason`。Helper 见 `rejectReason` 非空就再问一轮人话，不会把内部 JSON 甩到屏幕上。

### 13.1 推理

```cpp
ImagePrediction ImageRecognizer::PredictDetailFromMat(const cv::Mat& img_raw) {
    cv::Mat blob;
    cv::dnn::blobFromImage(img_raw, blob, 1.0 / 255.0,
        cv::Size(input_width, input_height),
        cv::Scalar(), /*swapRB=*/true, /*crop=*/false);
    // 再按 ImageNet mean/std 逐通道标准化（blobFromImage 的 scalefactor 只能是标量）

    Ort::Value input_tensor = Ort::Value::CreateTensor<float>(
        memory_info, blobData, input_tensor_size, dims.data(), dims.size());
    // 借用 blob 内存，blob 必须活到 Run 结束

    auto output_tensors = session->Run(...);

    const size_t num_classes =
        output_tensors.front().GetTensorTypeAndShapeInfo().GetElementCount();
    // 必须用张量长度。用 labels.size() 会在标签多一行时读越界。

    const size_t pred_class = max_element(...) - output_data;

    const float maxLogit = output_data[pred_class];
    double sumExp = 0.0;
    for (size_t i = 0; i < num_classes; ++i)
        sumExp += std::exp(static_cast<double>(output_data[i]) - maxLogit);

    result.confidence = sumExp > 0.0 ? static_cast<float>(1.0 / sumExp) : 0.0f;
    result.label = (pred_class < labels.size()) ? labels[pred_class] : "Unknown";
    return result;
}
```

减最大 logit 再 exp：防止溢出，且不改变 softmax 结果（分子分母同乘常数）。最大项减自身后 exp 恒为 1，所以置信度是 `1/sumExp`。

旧接口 `PredictFromBuffer` 只回头，内部转调 `PredictDetail*`。

## 十八、知识库灌库（共享 RAG）

问仍走 `AliyunRAGStrategy` + `Knowledge_Base_ID`（应用 ID）。上传文档是另一条路，不和识图 `/upload` 混。

```
菜单 [3] → GET /kb → kb.html
POST /kb/upload  { filename, file: base64 }
  鉴权 + canChat
  BailianKnowledgeClient::ingest
    1. POST /{WorkspaceId}/datacenter/category/{CategoryId}   申请租约
    2. PUT  租约 URL，二进制文件（不要 FormData）
    3. PUT  /{WorkspaceId}/datacenter/file                    AddFile
    4. POST /{WorkspaceId}/index/add_documents_to_index       追加索引
  返回 fileId + jobId（此时索引多半还在跑）
POST /kb/job-status { jobId } → COMPLETED / FAILED / RUNNING / PENDING
```

环境变量：`BAILIAN_WORKSPACE_ID`、`BAILIAN_INDEX_ID`（知识库 IndexId，**不是** `Knowledge_Base_ID`）、可选 `BAILIAN_CATEGORY_ID`（默认 `default`）。Key 仍用 `DASHSCOPE_API_KEY`。

共享库：任何人传上去的文档，别人选「百炼RAG」也能问到。这是产品设定，不是漏做隔离。

## 十九、和旧印象不要对上的地方

| 旧写法 | 现在 |
|---|---|
| `vector<pair<string,long long>>`，`i%2` 当 role | `ChatMessage.role` |
| Handler `lock_guard` + `operator[]` | `shared_mutex` 访问器，读用 `find` |
| 每请求 `AIConfig config; loadFromFile` | `instance()` + `call_once` |
| MQ 里拼 SQL + `escapeString` | JSON，消费端 `?` |
| 识图不落库，confidence 写死 0.95 | `image_result` + softmax |
| `/chat/send` 占死 IO 线程回 JSON | worker 池 + SSE（RAG 除外） |
| 临时提示词当正式历史 | MCP 才有，当场 pop |
| 同窗口换模型另存一份 | 同一 Helper、同一张表；整段历史交给当前策略 |
